## Verdict

`useAuth()` can return the throwing default only when React cannot find the **same `AuthContext` object** above the consumer. There is no token, cache, API, loading, or provider-state path that replaces the real guard with the default guard.

Therefore, if the stack resolves to `dist/src/auth.js:126` or source-maps to `src/auth.tsx:169`, the consumer is either:

1. Outside the matching provider’s React ancestry, or
2. Using a second evaluation/copy of the auth package: `Context_A !== Context_B`.

The second case is the strongest risk in the current Module Federation setup.

## Concrete failing runtime path

Normal package path:

1. Resolve `@bri/addons-auth-provider` through `package.json:5`.
2. `dist/src/index.js:4-7` loads/re-exports `dist/src/auth.js`.
3. Module evaluation creates `AuthContext_A` at `dist/src/auth.js:267`.
4. `AuthProvider_A` supplies `valueMemoized.guard` at `:1086`, through the provider at `:1192`.
5. A descendant’s `useAuth_A()` at `:1195` receives that value and calls the real guard at `:318`.

Failure path:

1. Provider renders `AuthContext_A.Provider`.
2. Consumer imports another package/module evaluation and executes `useAuth_B()`.
3. React searches for `AuthContext_B.Provider`; `AuthContext_A.Provider` is irrelevant.
4. No `B` provider is found, so React returns `AUTH_INITIAL_VALUES_B`.
5. `guard()` executes the default at `dist/src/auth.js:118-126` and rejects with `Function not implemented.`

Ordinary Node resolution of the root entry and `dist/src/auth` was verified to produce identical `AuthProvider` and `useAuth` exports. The mismatch therefore needs distinct physical modules, source-versus-dist imports, federation containers/share scopes, aliases/symlinks, HMR duplication, or separate package names.

## Conditions that can produce it

- Consumer is a sibling/ancestor of the provider, or invokes `useAuth` in the same component that later returns `<AuthProvider>`.
- Provider is conditionally omitted or an error-boundary fallback containing the consumer is outside it.
- Consumer is mounted through another `createRoot`, iframe, or independently bootstrapped MFE. DOM containment does not carry React context; ordinary React portals do.
- Provider and hook come from different package copies or versions.
- One side imports published `dist`, while another aliases/transpiles the included `src/auth.tsx`.
- Module Federation does not enforce the auth package as a singleton.
- `@bri/addons-auth-provider` and `@ordentco/addons-auth-provider` are mixed. They are always distinct contexts even if their implementation is nearly identical.
- Dev HMR/module reset preserves an old provider while a newly evaluated hook references a new context.

API rejection, no token, session-cache parsing, or an uninitialized provider cannot produce this exact guard stub.
