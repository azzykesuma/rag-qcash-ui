# Investigation result

## Executive conclusion

1. **`qcash-global-component` has an `AuthProvider`, but only in its own Next.js `_app`.** It wraps locally rendered pages, not Module Federation exports consumed by another application.
2. **A remotely consumed component is wrapped only by the consuming host’s React tree.** Loading `remoteEntry.js` does not boot the remote’s `_app`.
3. **Thirteen exposed entry points have a direct or transitive path to `useAuth`.** A fourteenth, `./modal-single-action`, uses `useGlobalStore` from the same package.
4. The remote correctly declares `@ordentco/addons-auth-provider` as a singleton, and explicitly makes client React/ReactDOM singletons. However, singleton behavior is only guaranteed within a correctly shared and initialized share scope.
5. **Ordinary remote network/load timing is not a convincing explanation for permanently receiving Guest/null/false values.** All `useAuth()` calls happen during render, so a lazily loaded component rendered under the correct provider sees the current context and later updates.
6. Timing can still matter in two narrower ways:
   - auth hydration is asynchronous, producing transient default values;
   - share-container initialization can affect which package version is selected.
7. **Permanent default auth values strongly indicate one of:**
   - no host `AuthProvider` ancestor;
   - a separate `@ordentco/addons-auth-provider` instance/share scope;
   - a separate React instance;
   - only `AuthProvider` but no matching `GlobalStoreProvider`.
8. There is meaningful version/lock drift:
   - remote manifest: auth `0.9.140-mfe`;
   - remote `yarn.lock`: stale `0.9.126-mfe`;
   - current host manifest/lock: `0.9.138-mfe`;
   - host does not explicitly mark the auth package singleton.

### What singleton does and does not guarantee

`singleton: true` helps only when:

- host and remote use the same share key;
- the remote container receives the host’s correct share scope;
- both are in the same Module Federation runtime/share scope;
- no custom loader bypasses container initialization.

It does not merge contexts across:

- separate runtime instances;
- different share scopes;
- an unshared host bundle and a remote fallback;

# 9. Load timing versus duplicate package/context

## Ordinary remote loading timing

Every identified `useAuth()` occurs inside a component or hook at render time. None is evaluated at module top level.

Therefore:

1. remote JavaScript can load before the provider;
2. the component can later be rendered below the provider;
3. `useContext` then reads the provider’s current value.

The import does not permanently capture the default context value.

In the current host, children are underneath dynamically loaded provider components, so they are not rendered first and wrapped later:

- `D:\work\qcash-ui\pages\_app.tsx:169-192`
- `D:\work\qcash-ui\components\providers\BRIProviders.tsx:46-50`

## Auth hydration timing

This can matter transiently.

The provider synchronously initializes only the token from local storage:

- `D:\work\qcash-global-component\node_modules\@ordentco\addons-auth-provider\dist\src\auth.js:234-239`

Username, user type, company IDs and authorities initially remain defaults:

- `...dist\src\auth.js:241-252`

`guard()` later hydrates them and sets readiness:

- cached hydration: `...dist\src\auth.js:275-303`
- validation starts with readiness false: `...dist\src\auth.js:320-330`
- completed authorities become ready: `...dist\src\auth.js:446-449`

The remote project itself does not call `guard()` from `_app`. The current host calls it asynchronously through `AuthBridgeSync`:

- `D:\work\qcash-ui\components\providers\AuthBridgeSync.ts:271-287`

None of the remote’s exposed auth consumers checks `isAuthoritiesReady`. Thus they can briefly render Guest/disabled/hidden states before hydration. With the correct context instance they should rerender afterward.

## Duplicate auth-package instance

If the host has package instance A and the remote consumes package instance B:

```text
Host AuthProvider_A
  └─ Remote component
       └─ useAuth_B() → AuthContext_B default
```

React ancestry alone cannot bridge `AuthContext_A` to `AuthContext_B`; the context object identity is different. This produces persistent Guest/null/false values and default callbacks even after host auth is ready.

## Duplicate React instance

If the host renderer uses React A while the remote hook uses React B, the common outcome is an invalid-hook-call/null-dispatcher error rather than merely Guest defaults.

Thus:

- **Guest/null/false without an invalid-hook error:** suspect duplicate auth context or no provider.
- **Invalid hook call:** suspect duplicate React.
- **Defaults that later correct themselves:** suspect normal auth hydration timing.
- **Behavior changing according to which remote initializes first:** suspect share-version/scope negotiation.

# Recommended interpretation and corrective actions

1. **Do not rely on the remote `_app`; it never wraps remote consumers.**
2. Ensure the host provides both `AuthProvider` and `GlobalStoreProvider` from the same shared package factory.
3. Mark `@ordentco/addons-auth-provider` as `singleton: true` in the host as well as the remote.
4. Align host and remote auth versions instead of relying on `requiredVersion: false`.
5. Align React/ReactDOM versions and verify they resolve from one share scope.
6. Ensure runtime-loaded remotes are initialized with the same webpack/default share scope.
7. Gate authority-sensitive components on `isAuthoritiesReady` to prevent transient authorization UI.
8. Remove lock drift and use one package manager with a frozen lock.
9. Add a host-level integration test that renders an exposed auth-sensitive component under the real shared providers; current component tests largely mock `useAuth`, so they do not validate Module Federation context identity.

The strongest diagnostic distinction is: **persistent defaults indicate missing/duplicate context; transient defaults indicate hydration; invalid-hook errors indicate duplicate React.**
