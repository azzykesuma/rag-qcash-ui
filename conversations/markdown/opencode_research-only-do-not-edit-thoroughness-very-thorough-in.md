## Executive conclusion

- The shell-owned browser route is **`/v2/dashboard-auto-collection/dashboard`**. Next strips `/v2`, so `router.pathname` is `/dashboard-auto-collection/dashboard`.
- `qcash-ui` owns route resolution, runtime remote registration, auth providers, session handling, and the router context.
- The exposed dashboard receives `router={router}`, but the remote component does not declare or use that prop. The remote itself performs no application-route navigation.
- Ordinary navigation into and away from the page is owned by the **`qcash-ui-header-footer`** remote. Its menu data and href are supplied by backend `/menu/me` and product/auth responses, not statically configured in `qcash-ui`.
- Header/menu/breadcrumb/footer are directly involved because the host wraps this page with `qcash-ui-header-footer/default`. The footer itself is passive; menu, breadcrumb, and header actions own navigation.
- The remote’s `_app.tsx` does **not** wrap the component when consumed through Module Federation. In host mode, it depends on the host’s shared auth/i18n/React providers.

# 12. Confirmed risks

1. **Broken/intermediate breadcrumb route**  
   `Port Solution` links to `/dashboard-auto-collection`, but the host has no matching index page. The only host page is `/dashboard-auto-collection/dashboard`.

2. **Router prop is a dead integration contract**  
   The host passes `router`, but the exposed component ignores it. Any future remote code assuming host-router injection would not currently receive it through a declared API.

3. **Remote `_app` providers are bypassed in host mode**  
   The exposed page relies entirely on compatible shared host auth/i18n/React instances. This is intentional-looking but creates a strict federation dependency.

4. **No host-controlled navigation callback on this layout**  
   A safer `HostHeaderFooterLayout` exists and passes `onNavigate`:
   - `D:\work\qcash-ui\components\federation\host-header-footer-layout.tsx:29-52`

   - `D:\work\qcash-ui-header-footer\layouts\default\index.tsx:4-6`

5. **Menu routing is based on substring `"v2"` rather than `router.basePath`**  
   Navigation behavior depends on backend href formatting:
   - `D:\work\qcash-ui-header-footer\layouts\default\container\menu\components\MenuModalProvider.tsx:102-116`

6. **Blank loading boundaries**  
   Both layout and dashboard render `null` while loading:

7. **Version skew is real**

8. **Large Next/MF implementation skew**

9. **Environment-inconsistent internal remote endpoints**

# 13. Hypotheses requiring runtime or backend confirmation

1. **Actual menu href may be correct or broken**  
   For SPA navigation, backend menu/product data should provide `/v2/dashboard-auto-collection/dashboard`. If it provides `/dashboard-auto-collection/dashboard`, header/footer will perform a hard navigation outside the shell base path. The actual production menu row is not in these repositories.

2. **Hard-coded remote URLs may be dormant in host mode**  
   The remote prefers an existing federation runtime, so the host-registered environment-aware QUI/global URLs may win. This needs browser inspection of the actual network requests.

3. **Version skew may or may not cause duplicate contexts**  
   Singleton configuration should select the host’s Ordent provider, but this should be confirmed via runtime share-scope inspection because the build/runtime stacks differ significantly.

4. **Transient unstyled rendering is possible**  
   Route CSS loading and page component loading are independent and not awaited by one common visible boundary. The dashboard’s style restoration helps after CSS has loaded once but cannot restore CSS before its first successful load.

5. **Auth can remain on the loader if sharing fails**  
   The dashboard waits for shared auth state and calls `guard()`. If it receives a separate provider instance rather than the host instance, the exposed component has no local `AuthProvider` and can remain unready.
