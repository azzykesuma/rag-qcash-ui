### Root Cause Analysis: Stale Session Leak Across User Switches

When switching users (e.g., from `ba` to `cu`) without a clean UI logout (such as tampering with or replacing tokens in `localStorage`), the stale session issue stems from a multi-layer caching and state invalidation breakdown spanning **`qcash-ui-header-footer`**, the **`addons-auth-provider`**, and the **`qcash-ui`** host shell.

---

### 1. Issues in `qcash-ui-header-footer`

#### A. One-Time Fetch Lock in [`useMenu.tsx`](file:///D:/work/qcash-ui-header-footer/hooks/useMenu.tsx#L23-L96)
```tsx
const hasFetched = useRef(false);

useEffect(() => {
  if (!(userType && !hasFetched.current)) {
    return;
  }
  hasFetched.current = true;
  const token = localStorage.getItem("access-token") as string;
  validateMenu.run(token);
  productRoles.run();
}, [userType]);
```
- **The Bug:** `hasFetched.current` is set to `true` during the first user's session (`ba`). Because it is stored in a ref and never reset when `token` changes, `!(userType && !hasFetched.current)` evaluates to `true` (skipping execution) when `cu` logs in.
- **Missing Dependency:** The effect only listens to `[userType]`, ignoring changes to `token`.

#### B. Static In-Memory Cache Keys in `useRequest` ([`useMenu.tsx#L31-L41`](file:///D:/work/qcash-ui-header-footer/hooks/useMenu.tsx#L31-L41))
```tsx
const validateMenu = useRequest(getMenu, {
  cacheKey: "validate-menu",
  staleTime: STALE_TIME, // 3 minutes
  manual: true,
});
```
- **The Bug:** ahooks' `useRequest` cache is globally keyed by the static string `"validate-menu"`. When `cu` logs in within 3 minutes of `ba`, `useRequest` serves `ba`'s cached menu response directly from memory instead of calling `/menu/me`.

#### C. Stale `localStorage` Fallback ([`useMenu.tsx#L66-L76`](file:///D:/work/qcash-ui-header-footer/hooks/useMenu.tsx#L66-L76))
- If remote data is still loading or if `productMenu` in global store is empty, `useCreation` falls back to `JSON.parse(localStorage.getItem("productMenu"))` and `localStorage.getItem("validateMenu")`, which contain the previous user's menus.

---

### 2. Issues in `addons-auth-provider` (`src/auth.tsx`)

#### A. Token-Agnostic 5-Minute Cache in [`guard()`](file:///D:/work/addons-auth-provider/src/auth.tsx#L363-L412)
```tsx
const sessionUserDataStr = sessionStorage.getItem("session-user-data");

if (useCache && sessionUserDataStr) {
  const sessionUserData = JSON.parse(sessionUserDataStr);
  const sessionValidatedAt = sessionUserData.sessionValidatedAt;
  
  if (sessionValidatedAt && Date.now() - sessionValidatedAt < SESSION_VALIDITY_MS) {
    setUsername(sessionUserData.username || "Guest");
    setUserType(sessionUserData.userType || null);
    setMenus(sessionUserData.menus || []);
    // Restores ba's profile and authorities, then returns early!
    return;
  }
}
```
- **The Bug:** `session-user-data` stored in `sessionStorage` has **no token or user hash association**. It only checks `Date.now() - sessionValidatedAt < 5 minutes`.
- When `cu` logs in within 5 minutes, `guard(true)` sees the fresh timestamp from `ba` and restores `ba`'s username, userType, menus, and authorities.
- Furthermore, the in-memory state [`sessionLastValidatedAt`](file:///D:/work/addons-auth-provider/src/auth.tsx#L404-L411) also causes non-cache `guard()` calls to exit immediately if called within 5 minutes while the React tree remains mounted.

#### B. Login Methods Do Not Invalidate Previous Session Caches ([`auth.tsx#L744-L771`](file:///D:/work/addons-auth-provider/src/auth.tsx#L744-L771), [`L1027-L1076`](file:///D:/work/addons-auth-provider/src/auth.tsx#L1027-L1076))
- `login()`, `passwordLogin()`, `passwordLoginWithCheck()`, and `ssoLogin()` set `access-token` in `localStorage`, but **do not**:
  1. Clear `sessionStorage.removeItem("session-user-data")`.
  2. Reset `sessionLastValidatedAt` to `null`.
  3. Clear `localStorage` keys (`productMenu`, `validateMenu`, `productRoles`).
  4. Reset user profile states (`username`, `userType`, `menus`, `authorities`).

---

### 3. Issues in `qcash-ui` (Host Shell)

#### A. Ineffective Token Invalidation in [`AuthBridgeSync.ts`](file:///D:/work/qcash-ui/components/providers/AuthBridgeSync.ts#L273-L289)
```tsx
const ordentTokenChanged = !!ordentAuth?.token && lastValidatedTokenRef.current.ordent !== ordentAuth.token;
if (shouldHydrateAuth(ordentAuth) || ordentTokenChanged) {
  // Calls ordentAuth.guard()
  Promise.resolve(ordentAuth.guard()).catch(...);
}
```
- While `AuthBridgeSync` notices the token change and calls `ordentAuth.guard()`, `ordentAuth.guard()` exits immediately due to the 5-minute `session-user-data` / `sessionLastValidatedAt` cache in `addons-auth-provider`.
- `AuthBridgeSync` then calls `syncLocalStorage()` and updates `window.__QCASH_AUTH_BRIDGE__` with the stale `ba` data.

#### B. Incomplete Route Cleanups in [`qcash-ui/pages/_app.tsx`](file:///D:/work/qcash-ui/pages/_app.tsx#L102-L111)
- The cleanup effect only targets `["/landing-page", "/v2/landing-page"]`. Logins happening via `/main-page`, modals, or direct redirects bypass this cache purge.

| Component | Stale Item | Why It Persists |
| :--- | :--- | :--- |
| **`addons-auth-provider`** | User Profile (`username`, `userType`, `companyCode`, `authorities`) | `guard()` restores `session-user-data` from `sessionStorage` or skips validation via `sessionLastValidatedAt` (< 5 min). |
| **`qcash-ui` (Host)** | Global Bridge & `localStorage` (`productMenu`, `validateMenu`) | `AuthBridgeSync` propagates the un-invalidated `ordentAuth` state back into `localStorage`. |
| **`qcash-ui-header-footer`** | Menu Items & Profile Dropdown | `hasFetched` ref prevents re-run, static `cacheKey` in `useRequest` serves cached response, and fallback parses stale `localStorage`. |

### Why the Root Cause Persists Without `AuthBridgeSync`:

#### 1. In `@ordentco/addons-auth-provider` (`src/auth.tsx`):
1. **Blind 5-Minute Cache in [`guard()`](file:///D:/work/addons-auth-provider/src/auth.tsx#L363-L412):**
   - When BA logs in, `sessionStorage.setItem("session-user-data", ...)` stores BA's data along with `sessionValidatedAt: Date.now()`.
   - When CU logs in within 5 minutes, `guard()` checks `Date.now() - sessionValidatedAt < 5 minutes`. Because **the cache is not bound to a specific token or user ID**, it unconditionally restores BA's `username`, `userType ("ba")`, `companyCode`, `menus`, and `authorities`.
   - In-memory `sessionLastValidatedAt` also causes `guard()` to exit immediately without contacting the backend.
2. **Login functions do not wipe previous session state:**
   - [`login()`](file:///D:/work/addons-auth-provider/src/auth.tsx#L1027) / [`passwordLogin()`](file:///D:/work/addons-auth-provider/src/auth.tsx#L744) overwrite the token in `localStorage`, but leave `sessionStorage.getItem("session-user-data")` and stale `localStorage` menus intact.

#### 2. In `qcash-ui-header-footer` (`hooks/useMenu.tsx`):
1. **One-Time Fetch Lock ([`useMenu.tsx#L23`](file:///D:/work/qcash-ui-header-footer/hooks/useMenu.tsx#L23)):**
   - `hasFetched = useRef(false)` becomes `true` after BA's fetch and never resets when a new user logs in.
2. **Static ahooks Cache Keys ([`useMenu.tsx#L31-L41`](file:///D:/work/qcash-ui-header-footer/hooks/useMenu.tsx#L31-L41)):**
   - `useRequest` uses a static `cacheKey: "validate-menu"` with a 3-minute `staleTime`, returning BA's menu from in-memory cache.
3. **Stale `localStorage` Fallback ([`useMenu.tsx#L66-L75`](file:///D:/work/qcash-ui-header-footer/hooks/useMenu.tsx#L66-L75)):**
   - Falls back to reading `localStorage.getItem("productMenu")` and `localStorage.getItem("validateMenu")`, which still contain the BA data.
4. **Header Profile Display:**
   - [`Header`](file:///D:/work/qcash-ui-header-footer/layouts/default/container/header/index.tsx#L9) and [`AvatarDropdown`](file:///D:/work/qcash-ui-header-footer/layouts/default/container/header/components/AvatarDropdown.tsx#L87) get `username`, `companyName`, `companyCode` directly from `useAuth()`. Since `useAuth()` was hydrated with BA's session from `sessionStorage`, the header displays BA info.

---

### What Needs to Be Fixed:

1. **In `@ordentco/addons-auth-provider`:**
   - In `guard()`: Check that the cached `session-user-data` token matches the currently active `access-token` before restoring it. If it doesn't match, purge the cache and force a new backend validation.
   - In `login()`, `passwordLogin()`, `ssoLogin()`: Clear `sessionStorage.removeItem("session-user-data")`, reset `sessionLastValidatedAt` to `null`, and remove stale `productMenu` / `validateMenu` from `localStorage`.
2. **In `qcash-ui-header-footer` (`useMenu.tsx`):**
   - Track `access-token` in `useEffect` and reset `hasFetched` when the token changes.
   - Scope ahooks `cacheKey` to the active token/user or clear the cache on token transition.

### Why It Refreshed on `dev` (The Reload Mechanism)

In the `dev` branch of [`qcash-ui/pages/_app.tsx`](file:///D:/work/qcash-ui/pages/_app.tsx#L94-L111), two specific hooks were added to force cache invalidation:

```tsx
// 1. Hard page reload when redirected with ?logout=true
useEffect(() => {
  if (typeof window !== "undefined" && router.query["logout"] === "true") {
    window.location.replace(window.location.pathname);
  }
}, [router.query]);

// 2. Storage purge on landing page
useEffect(() => {
  if (typeof window === "undefined") return;
  const isLandingPage = ["/landing-page", "/v2/landing-page"].includes(router.pathname);
  if (isLandingPage) {
    sessionStorage.removeItem("session-user-data");
    localStorage.removeItem("productMenu");
    localStorage.removeItem("productRoles");
    localStorage.removeItem("validateMenu");
  }
}, [router.pathname]);
```

### The Sequence That Occurred in Your Local Test:

1. When you tampered with the `access-token` on the authorized page, the auth failure (401) routed the app to `/landing-page?logout=true`.
2. On `dev`, the first hook in `_app.tsx` detected `router.query["logout"] === "true"` and triggered **`window.location.replace(...)`** (a full browser page reload).
3. **What the Hard Page Reload did:**
   - Completely destroyed the JavaScript memory space.
   - Cleared the React Provider's in-memory state (`sessionLastValidatedAt`).
   - Flushed ahooks' in-memory `useRequest` cache (`"validate-menu"`).
   - Reset the one-time fetch ref in Header-Footer (`hasFetched.current = false`).
4. On reload at `/landing-page`, the second hook executed and purged `session-user-data` from `sessionStorage` and menu items from `localStorage`.
5. When you entered `cu` credentials, the application started with completely clean storage and memory, fetching fresh `cu` credentials.

---

### Why It Fails on Production (`v1.655.1-release-com`):

On the production branch **`v1.655.1-release-com`**, neither of these two hooks exists in `pages/_app.tsx`:

| Behavior | `qcash-ui` (`dev`) | `qcash-ui` (`v1.655.1-release-com` Prod) |
| :--- | :--- | :--- |
| **Route to `?logout=true`** | Triggers `window.location.replace` (Hard Reload). | Client-side Next.js route transition (No Reload). |
| **In-Memory Singletons / Refs** | Completely wiped by reload. | Stay alive in memory (`hasFetched = true`, ahooks cache retained). |
| **`sessionStorage` (`session-user-data`)** | Explicitly removed by `_app.tsx`. | **Persists** (restored by `guard()` within 5 minutes). |
| **`localStorage` (`productMenu`, etc.)** | Explicitly removed by `_app.tsx`. | **Persists** (fallback used by `useMenu.tsx`). |

---

### Summary

The reason you could not reproduce the issue on `dev` is because the `dev` branch of `qcash-ui` has an explicit **workaround** in `_app.tsx` that forces a full browser reload on logout and wipes storage on the landing page.

In **production (`v1.655.1-release-com`)**, without that workaround:
- Next.js performs a client-side route transition without reloading.
- `session-user-data` in `sessionStorage` and the in-memory caches are never purged.
- When `cu` logs in, `guard()` restores `ba` from `sessionStorage` because it is less than 5 minutes old.
