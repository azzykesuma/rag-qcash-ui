This behavior is caused by a timing and state-management gap in the original codebase, and **your changes did not affect or cause this.**

Here is the technical explanation of why they close at different times and how the issue occurs:

---

### 1. Mismatched Modal Closure & Error Display
There are two main reasons for this behavior:

#### A. Missing `await` in the custom submission handler (`customFn`)
In [view-page.tsx](file://~/Development/qcash-ui-user-management/containers/view-page.tsx#L86-L95) and [table-home-user.tsx](file://~/Development/qcash-ui-user-management/containers/user-index/table-home-user.tsx#L536-L545), `customFn` executes the API call using `approveAction`, but it **does not `await` the response**:

```typescript
// containers/view-page.tsx
const customFn = async (param: any) => {
  const { values, setIsLoading } = param;
  setIsLoading(true);
  
  // ❌ Missing "await" before approveAction!
  approveAction(
    values.taskID,
    action === "delete" ? "approve" : action,
    ...
  );
};
```

Because of the missing `await`, `customFn` returns immediately with a resolved `undefined` Promise. The OTP transaction modal (`ModalOTP`) assumes the submission process was triggered successfully and stops its internal loading spinner. 

Meanwhile, `approveAction` runs in the background. When the API response finally returns with `"Hard Token Validation Fail"`:
1. `approveAction` catches the error and triggers the global `ResponseModal` to show the error popup.
2. The `ModalOTP` remains open on the screen because it was never notified of the failure.

---

#### B. Missing `onClose` prop on `<ModalOTP>`
In both components, `ModalOTP` is rendered without passing the `onClose` handler returned by the `useModal` hook:

```typescript
// ❌ transactionModalProps contains "open: true", but no "onClose" is passed
<ModalOTP {...transactionModalProps} actionFn={customFn} />
```

Inside the `ModalOTP` component (which is loaded from `qcash-global-component`), when the user clicks the close or cancel button, it tries to call `onClose()`. Because it's not passed, it defaults to a no-op (`() => {}`), meaning the parent's `open` state remains `true`, preventing the modal from closing cleanly.

---

### How to Fix It (Optional)

If you want to align their closure times and handle the error inside the transaction modal properly, you can make these two adjustments:

1. **Destructure `closeModalTransaction` and pass it to `onClose`**:
   ```typescript
   // Destructure the 3rd argument (closeModal)
   const [transactionModalProps, openModalTransaction, closeModalTransaction] = useModal<TransactionModalProps>();
   
   // ...
   
   // Pass it to the component
   <ModalOTP {...transactionModalProps} actionFn={customFn} onClose={closeModalTransaction} />
   ```

2. **Add `await` and re-throw the error inside `approveAction`**:
   Currently, `approveAction` catches the error internally and doesn't re-throw it. If you `await approveAction(...)` and let it propagate the rejection, `ModalOTP`'s internal form handler will catch the failure and display the error directly inside the OTP modal's alert box instead of launching the separate global `ResponseModal`.

The parent hooks (`useModal` for transaction modal and `useModal` for response modal) trigger state updates inside an asynchronous API catch block (`approveAction`'s `.catch()` or `try...catch`).
- **The Issue**: React handles state batching differently depending on the React version and the browser's JavaScript engine microtask queue. 
  - In React 18, updates inside promises/async-catch are batched automatically.
  - In React 17 (or depending on polyfills), async updates are **not** batched by default. This can cause one browser to batch both state changes (`hideModalResponse` + `closeModalTransaction`) into a single render pass, while another browser schedules them across multiple microtask ticks, rendering them visibly "out of sync".
- **The Solution**: We can guarantee synchronous execution and force React to batch these updates across all browsers by wrapping them in `ReactDOM.unstable_batchedUpdates` (if needed).
