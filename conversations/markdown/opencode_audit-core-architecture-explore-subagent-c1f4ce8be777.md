# 2. Verified responsibilities and runtime relationships

## `qcash-ui`: active shell and route façade

The current shell is more than the simple static Module Federation host described in the document:

- It owns the browser route tree under `basePath: "/v2"`:  
  `~/Development/qcash-ui/next.config.js:66-70`
- Its webpack federation configuration has **no static remotes**:  
  `~/Development/qcash-ui/next.config.js:8-13`
- Instead, it discovers every feature from a registry, resolves entries, and initializes `@module-federation/runtime` in the browser:  
  `~/Development/qcash-ui/services/federation/init.ts:32-68`
- The registry associates remote applications with routes and environment toggles. Relevant mappings include:
  - main page: `~/Development/qcash-ui/constants/features/registry.ts:59-62`
  - dashboard: `~/Development/qcash-ui/constants/features/registry.ts:64-72`
  - BRI header: `~/Development/qcash-ui/constants/features/registry.ts:529-534`
  - landing page: `~/Development/qcash-ui/constants/features/registry.ts:589-598`
- Route wrappers load exposed remote components client-side. For example, `/homepage` composes the normal header/footer around the dashboard:  
  `~/Development/qcash-ui/pages/homepage/index.tsx:9-27`
- It owns:
  - dual auth-provider roots;
  - session-expiry/relogin modal;
  - auth bridging;
  - federation retry/fallback and global styles;
  - route-scoped remote preloading;
  - shell-level i18n synchronization.

The root provider order is:

```text
@bri AuthProvider + GlobalStore
  └─ @ordentco AuthProvider + GlobalStore
       └─ Qui provider
            └─ AuthBridgeSync
                 └─ remote page/layout
```

Evidence:  
`~/Development/qcash-ui/components/providers/BRIProviders.tsx:7-50`  
`~/Development/qcash-ui/pages/_app.tsx:163-197`

# 4. Technical debt, architecture gaps and tight coupling

## Critical

### C1. The auth bridge contract is structurally broken

The host’s bridge data contains only a small subset:

`~/Development/qcash-ui/components/providers/AuthBridgeSync.ts:54-73`  
`~/Development/qcash-ui/components/providers/AuthBridgeSync.ts:196-212`

The header’s independently declared bridge contract expects many absent fields, including `token`, `userID`, `companyID`, products, stores and actions:

`~/Development/qcash-ui-header-footer/layouts/default/AuthBridge.tsx:6-50`

Consequences:

- `bridgeData.token` is normally absent;
- `bridgedProducts` is absent;
- consumers silently fall back to localStorage and provider stores:  
  `~/Development/qcash-ui-header-footer/hooks/useMenu.tsx:183-203`
- there is no shared package or compile-time contract between producer and consumer.

This is tight coupling through a magic window key and custom DOM event.

### C2. Host replication calls setters that the local BRI provider does not expose

`AuthBridgeSync` attempts setters such as `setUsername`, `setCompanyID`, `setAuthorities`, `setProductAuthorities` and `setIsAuthoritiesReady`:

`~/Development/qcash-ui/components/providers/AuthBridgeSync.ts:302-357`

The local auth-provider context only exports `setToken`, `setUserType` and `setIsLoading` among state setters:

`~/Development/addons-auth-provider/src/auth.tsx:1115-1128`

Because bridge calls are guarded by `typeof setter === "function"`, the missing setters fail silently. The comment claiming complete Ordent-to-BRI replication is therefore false for the audited local package. On BRI-preferring routes this can leave the BRI context tokenized but unhydrated or guest-like.

### C3. Local `qcash-ui-main-page` package namespace is internally inconsistent

The uncommitted worktree manifest now installs only BRI auth:

`~/Development/qcash-ui-main-page/package.json:18`

But source and federation config still import/share Ordent:

`~/Development/qcash-ui-main-page/pages/_app.tsx:4`  
`~/Development/qcash-ui-main-page/pages/index.tsx:5`  
`~/Development/qcash-ui-main-page/next.config.js:18-22`

A clean install from the current worktree manifest can fail resolution or accidentally rely on stale `node_modules`.

## High

### H1. UI logout does not invalidate the backend token

Backend calls in provider logout are commented:

`~/Development/addons-auth-provider/src/auth.tsx:773-789`

The backend has real token deletion/jailing logic:

`~/Development/addons-auth-service/server/api/auth.go:124-171`

Until expiry, a copied token may remain usable after UI logout. This is a security and session-lifecycle gap.

### H2. The server’s global auth/role interceptors are disabled

The server constructs an auth interceptor:

`~/Development/addons-auth-service/server/main.go:312-318`

But both unary and stream auth interceptors are commented out:

`~/Development/addons-auth-service/server/interceptors/interceptor.go:45-56`  
`~/Development/addons-auth-service/server/interceptors/interceptor.go:59-68`

Some handlers validate tokens themselves, but there is no enforceable central boundary. Adding an endpoint without local validation can expose it unintentionally.

### H3. Auth-provider `login()` has a parameter-order defect

Public contract and implementation say:

```text
login(username, password, branchCode)
```

`~/Development/addons-auth-provider/src/auth.tsx:96-101`  
`~/Development/addons-auth-provider/src/auth.tsx:974-982`

But `AuthService.login` expects:

```text
login(branchCode, username, password)
```

`~/Development/addons-auth-provider/services/auth.ts:201-208`

The provider forwards arguments without reordering. Any consumer of that method sends credentials in the wrong fields.

### H4. The provider’s `apiUrl` prop does not control its legacy AuthService Axios instance

`AuthProvider` calls `setApiUrl(apiUrl)` for the newer Axios framework:

`~/Development/addons-auth-provider/src/auth.tsx:297-302`

But its own `AuthService` uses the separate legacy Axios singleton, whose base URL is fixed from package config at module initialization:

`~/Development/addons-auth-provider/services/custom-axios.ts:7-13`

Thus the provider advertises runtime API injection while its core validation/login methods may use a different hostname-derived URL.

### H5. Five divergent session-expiry implementations coexist

The shell, provider legacy Axios, provider new Axios, dashboard, header, landing and main-page each implement overlapping token clearing, queueing, redirects and status handling.

Examples:

- shell legacy statuses include 401/499/408:  
  `~/Development/qcash-ui/services/custom-axios.ts:83-129`
- provider new framework treats 401/499 as relogin and optionally 400 as fallback:  
  `~/Development/addons-auth-provider/src/global-custom-axios/interceptors/auth-interceptors.ts:489-556`
- dashboard has another queue and redirects to old `/main-page` in one mode:  
  `~/Development/qcash-ui-dashboard/services/custom-axios.ts:39-129`

Behavior depends on which remote issued the request, producing inconsistent second-expiry, retry and error handling.

### H6. The provider globally monkey-patches navigation APIs

The current feature branch patches:

- `Location.prototype.replace`;
- `Location.prototype.assign`;
- `Location.prototype.href`;
- Next Router singleton;
- `window.next.router`.

`~/Development/addons-auth-provider/src/global-custom-axios/interceptors/auth-interceptors.ts:314-457`

This is process-wide, undocumented runtime coupling. It can suppress legitimate navigation from unrelated MFEs and is difficult to test or safely unload.

### H7. Authority cache is not bound to a token/user identity

`guard(useCache=true)` restores `session-user-data` solely by timestamp:

`~/Development/addons-auth-provider/src/auth.tsx:306-340`

The cache object does not include or validate the access token/user ownership:

`~/Development/addons-auth-provider/src/auth.tsx:535-559`

Shell cleanup mitigates common paths, but token replacement, SSO or partial logout can temporarily hydrate a new session with the previous user’s permissions.

### H8. Login/guard error ordering can bypass controlled redirect

After `validateToken()` fails, `guard` stores the error as `response`, then calls `validateMenu` before it evaluates `response.status`:

`~/Development/addons-auth-provider/src/auth.tsx:368-425`

If menu validation also rejects, the intended refresh/clear/redirect branch is never reached.

### H9. Sensitive bearer tokens are kept in localStorage under a permissive CSP

Token storage is pervasive, for example:

`~/Development/qcash-ui-landing-page/zustand/useLogin.tsx:589-612`

The shell CSP allows both `'unsafe-eval'` and `'unsafe-inline'`, plus broad HTTP/HTTPS script sources:

`~/Development/qcash-ui/next.config.js:93-105`

This increases the impact of any XSS or compromised remote bundle.

### H10. Shell production builds suppress lint and TypeScript failures

`~/Development/qcash-ui/next.config.js:78-80`

This is especially dangerous in a host that dynamically integrates dozens of untyped remote contracts. Existing `@ts-ignore`, `any`, and producer/consumer bridge drift can reach deployment unchecked.

### H11. Remote entry caching policy is incomplete and currently uncommitted

The dashboard and main-page worktrees add `no-store` for `remoteEntry.js`, but those changes are not committed. Landing, normal header and BRI header lack equivalent policy.

Examples:

- uncommitted dashboard rule:  
  `~/Development/qcash-ui-dashboard/next.config.js:24-35`
- main-page rule:  
  `~/Development/qcash-ui-main-page/next.config.js:43-53`
- no corresponding header rule:  
  `~/Development/qcash-ui-header-footer/next.config.mjs:9-40`

Because `remoteEntry.js` has a fixed name, inconsistent caching can load stale manifests and singleton versions.

### H12. Remotes hardcode the shared-component development URL

Examples:

- landing: `~/Development/qcash-ui-landing-page/next.config.js:11-15`
- dashboard: `~/Development/qcash-ui-dashboard/next.config.js:8-12`
- BRI header: `~/Development/qcash-ui-header-footer-bri/next.config.js:8-11`
- main page: `~/Development/qcash-ui-main-page/next.config.js:7-10`

Standalone builds for non-development environments can still compile a dev-cluster remote URL, even though runtime code separately computes an environment-specific URL.

### H13. External V4 routing remains mock-only and embeds static JWTs

Only mock credentials are recognized:

`~/Development/addons-auth-service/server/api/auth_external_routing.go:74-89`

Mock V4 responses embed JWT-shaped access and refresh tokens in source:

`~/Development/addons-auth-service/server/api/auth.go:2677-2687`

Even if expired/non-production, hardcoded credentials in an authentication service are poor security hygiene and can mask missing integration.

### A. A current runtime matrix

For each core repository, document:

- role: host, remote, standalone app, library, service or legacy monolith;
- exposed module names;
- deployment `basePath`;
- standalone dev port;
- auth namespace in manifest;
- provider inherited when remote versus created when standalone;
- current canonical branch.

This would immediately clarify `addons-web-client`, `qcash-ui-main-page`, and both header implementations.

### B. A “runtime federation source of truth” section

State that:

- shell webpack `remotes` is intentionally empty;
- `/qcash-ui/constants/features/registry.ts` is the remote/route registry;
- entries derive from `baseFederation`;
- remote components are loaded client-side and do not execute remote `_app`;
- standalone remote startup is a different provider/runtime mode;
- fixed `remoteEntry.js` must use one cross-repo cache policy.

### C. A dual-provider migration section

Document the actual current arrangement:

- shell mounts BRI and Ordent contexts;
- Ordent is presently the primary authority source;
- BRI-preferred routes are explicitly listed;
- the bridge uses `window.__QCASH_AUTH_BRIDGE__` and `qc-bridge-sync`;
- producer and consumer contracts are currently not shared;
- which setters/data are genuinely supported;
- criteria for deleting either provider.

Do not state that replication is complete until the bridge contract is corrected.

### D. Correct auth flow diagrams

Separate:

1. new landing V3 login;
2. old main-page V2 login;
3. SSO/VSSO;
4. MFA continuation;

Explicitly say that UI logout currently does not call backend token invalidation.

### G. A local-worktree warning

State that root docs describe committed architecture unless explicitly marked otherwise. Include a short command checklist to verify branch, dirty source/config files and provider versions before debugging cross-repo behavior.

## Bottom line

The broad MFE description remains valid, but the current system is actually a hybrid of:

- runtime-registry-based MFEs;
- dual auth contexts;
- a loosely typed global bridge;
- independent standalone provider roots;
- multiple incompatible Axios/session implementations;
- old and new login routes;
- and a still-present legacy Nx monolith.

The most urgent issues are the broken auth-bridge contract, unavailable BRI replication setters, browser-only logout, disabled centralized backend auth interception, and the current main-page auth-package mismatch.
