## 1. Legacy shared-component remote

`~/Development/qcash-global-component` is a private Next.js application, not an npm package:

- Private package, Next 13.5.6 and React 18: `~/Development/qcash-global-component/package.json:2-5`, `:52-60`.

- Emits `static/chunks/remoteEntry.js`: `~/Development/qcash-global-component/federation.config.js:2-5`.

### Architectural boundary violation

The repository is called “global component,” but exposed components directly import application services:

- Transaction modal imports Axios and transaction services: `~/Development/qcash-global-component/components/transaction-modal/index.tsx:2-35`.
- Bulk-action UI imports product, transfer, and transaction API services: `~/Development/qcash-global-component/components/table/bulk-action-modal.tsx:2-4`.

- Activity-log UI calls task APIs: `~/Development/qcash-global-component/components/activity-log/use-activity-log.ts:11`.

The remote therefore bundles UI, authorization assumptions, local-storage conventions, environment routing, transfer workflows, and backend API contracts. It is a shared application-runtime subsystem, not a neutral component library.

# Highest-priority findings

## Critical security

1. **Committed registry credential**
   - `~/Development/qcash-ui-design-system/config/bunfig.toml:1-2` contains a literal private-registry token.
   - Rotate/revoke it, remove it from history, and inject it through BuildKit secrets or CI credentials.

2. **Client-visible values named as secrets**
   - `~/Development/qcash-global-component/.env.example:11-12` defines signature/secret values under `NEXT_PUBLIC_*`.
   - Next.js embeds `NEXT_PUBLIC_*` values into browser bundles. They cannot be treated as secrets.
   - The Docker build explicitly passes the login secret into the client build: `~/Development/qcash-global-component/Dockerfile:87-94`.

3. **Registry password written into Docker layer**
   - `~/Development/qcash-global-component/Dockerfile:18-22` writes a Nexus password-derived value into `/tmp/pass` and `~/.npmrc`.
   - Even though this is an intermediate stage, build cache/layer access can expose it. Use secret mounts and remove credential material in the same layer.

## High architectural risk

1. **Builds intentionally accept type and lint failures**
   - `~/Development/qcash-global-component/next.config.js:10-15`.
   - This is especially risky for a remote consumed by dozens of independently deployed hosts.

2. **Missing direct Axios dependencies**
   - `qcash-global-component` imports Axios directly at `~/Development/qcash-global-component/services/api-service.ts:1`, but Axios is absent from its dependency list `~/Development/qcash-global-component/package.json:22-74`.
   - `qcash-ui-base` imports Axios at `~/Development/qcash-ui-base/services/custom-axios.ts:1`, but it is absent from `~/Development/qcash-ui-base/package.json:13-30`.
   - Both currently depend on undeclared transitive installation behavior.

3. **Federation compatibility is largely unchecked**
   - Legacy remote disables version requirements for nearly every shared package: `~/Development/qcash-global-component/federation.config.js:5-36`.
   - It lists `moment` as shared even though `moment` is not a declared dependency: `~/Development/qcash-global-component/federation.config.js:19`.
   - New producer similarly shares React with `requiredVersion: false`: `~/Development/qcash-ui-design-system/apps/producer/rslib.config.ts:58-64`.
   - Notebook uses React 19 while producer/packages develop against React 18:  
     `~/Development/qcash-ui-design-system/apps/notebook/package.json:38-40`  
     `~/Development/qcash-ui-design-system/apps/producer/package.json:40-46`

4. **Mutable, unversioned remote contracts**
   - Legacy package version remains `0.1.0`: `~/Development/qcash-global-component/package.json:2-4`.
   - New packages/producer remain `0.0.0`.
   - Consumers load fixed paths such as `/design-system/static/remoteEntry.js`, not immutable versioned assets.

# Recommended root architecture sections

The root `~/Development/ARCHITECTURE.md` should distinguish operational runtime from the physical directory listing. Recommended sections:

1. **Scope and terminology**
   - QCash/QLola naming
   - shell, MFE, remote, producer, component library, composite widget
   - what “runtime” excludes

2. **Repository taxonomy**
   - Production runtime
   - Runtime libraries under adoption
   - Templates/scaffolds
   - Experiments/POCs
   - Diagnostic tools/local overrides
   - Unrelated personal applications
   - Archived/superseded repositories

3. **Runtime topology**
   ```text
   QCash shells/MFEs
     ├── qcash-global-component remote
     ├── qui remote from qcash-ui-design-system/apps/producer
     ├── auth provider
     └── QCash APIs
   ```
   Include remote names, base paths, URLs by environment, owners, and deployment order.

4. **Legacy-to-QUI migration**
   - Which components remain in `qcash-global-component`
   - Which are available from `qui`
   - Naming/deprecation mapping for `new`/`v2` variants
   - Retirement criteria for the legacy remote
   - Explicit status of `~/Development/qui`

5. **Module Federation contracts**
   - Expose naming standards
   - Shared/singleton policy
   - React/Next compatibility matrix
   - Type generation and consumer handling
   - Backward-compatibility/deprecation rules
   - Immutable or versioned remote assets
   - Rollback and cache policy

6. **Design-system package layers**
   - Tokens/styles
   - icons
   - accessible primitives
   - generic composites
   - QCash business widgets such as transaction authorization
   - notebook versus producer responsibilities

7. **HTTP/auth/session architecture**
   - Owner of token attachment
   - 401/499/session-expiry behavior
   - `showDialog` event schema and lifecycle
   - retry/queue/fallback behavior
   - status of `@j45/custom-axios`
   - migration away from copied interceptors

8. **Environment and configuration contract**
   - Canonical names for prestage/predeploy
   - canonical hostname matching
   - client-public versus server-secret values
   - API base URL resolution ownership
   - validation at build/startup

9. **Package and release governance**
   - npm versus federation publication
   - registry ownership
   - versions/changelogs
   - supported React peer ranges
   - release promotion and rollback
   - consumer compatibility testing

10. **Security boundaries**
    - no committed registry tokens
    - no `NEXT_PUBLIC_*` secrets
    - Docker secret handling
    - local-storage/token assumptions
    - browser-extension host permissions and data retention

11. **Testing and quality gates**
    - required type/lint checks
    - remote contract tests
    - host/remote integration tests
    - accessibility/visual regression
    - prohibition on `ignoreBuildErrors` for shared runtime artifacts

12. **Ownership and lifecycle**
    - owner/on-call for each runtime remote
    - active, adopting, deprecated, archived status
    - last reviewed date
    - deletion/archive criteria for POCs and empty tooling directories

13. **Developer tooling appendix**
    - `qlola-nav-logger`
    - local overrides
    - MFE router POC
    - Sonar hook scripts
    - explicit warning that `voice_typer` and `whatsapp-blur` are outside QCash architecture

The immediate priorities are credential rotation, removal of client-visible “secrets,” restoration of mandatory type/lint gates, declaration of direct dependencies, and documenting/versioning the two deployed federation contracts.
