## Turn 69: Assistant

`qcash-ui-dashboard` still needs the `401 / 499 / 408` handler in [`services/custom-axios.ts`](file://~/Development/qcash-ui-dashboard/services/custom-axios.ts) for several key reasons:

---

### 1. Independent Axios Instance
- Dashboard services ([`services/index.ts`](file://~/Development/qcash-ui-dashboard/services/index.ts), [`services/force-update.ts`](file://~/Development/qcash-ui-dashboard/services/force-update.ts)) make all API requests (account summary, recent transactions, scheduled transactions, fast menu, forex, etc.) using the local [`customAxios`](file://~/Development/qcash-ui-dashboard/services/custom-axios.ts) instance created via `axios.create()`.
- Axios interceptors are **instance-scoped**, not global. Even though `@bri/addons-auth-provider` has its own Axios interceptor, it does not intercept requests made by dashboard's local `customAxios` instance. Without this handler, any expired token error would directly reject without triggering re-authentication.

---

### 2. Micro-Frontend Communication via `document.dispatchEvent("showDialog")`
- In QCash's Module Federation architecture, the host shell (`qcash-ui` / `qcash-header-footer`) owns the session expiration and re-login modal.
- The remote MFE communicates session expirations across Module Federation boundaries by dispatching:
  ```ts
  document.dispatchEvent(
    new CustomEvent("showDialog", {
      detail: { ...originalRequest, resolve, reject, queue, isDashboard: !isFlagNewQlola }
    })
  );
  ```
- The host shell listens for `showDialog`, displays the session expired popup, and once the user re-authenticates, resolves the pending requests in the `queue` so they retry seamlessly without reloading the whole page.

---

### 3. Dashboard-Specific Request & Route Logic
Dashboard's local interceptor contains logic specific to the dashboard that generic auth providers do not have:
- **`isDashboard` detail flag**: Informs the host modal whether the request originated from the homepage or new Qlola (`isDashboard: !isFlagNewQlola`), altering the modal's redirect and refresh behavior upon re-auth.
- **`Grpc-Metadata-Process_Id`**: Injected on `account-summary` endpoints via UUID.
- **Route-aware handling**: Handles `/v2/homepage` vs `/v2` vs `/main-page` differently (e.g. avoiding redirect loops if already logging out).

---

### 4. Standalone Mode Fallback
- When running `qcash-ui-dashboard` standalone (e.g. `yarn dev` on port 3003) where the host shell's modal listener is not mounted:
- If `newEventSessionExpired` is disabled or fails, it falls back to:
  ```ts
  localStorage.removeItem("access-token");
  localStorage.removeItem("refresh-token");
  localStorage.removeItem("login");
  window.location.replace("/main-page");
  ```
  preventing developers and standalone instances from being trapped in an invalid authenticated state.

## Turn 75: Assistant

**No, `@bri/addons-auth-provider`’s navigation changes do NOT automatically cover or affect the local `customAxios`.**

Here is why they are separate and how they interact:

---

### 1. Two Completely Different Layers

| Layer | Responsibility | Handled By |
|---|---|---|
| **Route / Navigation Guard** | Page-level access control, preventing users from landing on routes if unauthenticated or unauthorized. | `@bri/addons-auth-provider` (`AuthProvider` in [`pages/_app.tsx`](file://~/Development/qcash-ui-dashboard/pages/_app.tsx#L51)) |
| **HTTP Transport Interceptor** | Intercepting in-flight API requests and handling response status codes (401, 499, 408, 504). | Local [`services/custom-axios.ts`](file://~/Development/qcash-ui-dashboard/services/custom-axios.ts#L41) |

Because [`services/custom-axios.ts`](file://~/Development/qcash-ui-dashboard/services/custom-axios.ts) uses an independent `axios.create()` instance, it has its own interceptor chain that runs outside of `@bri/addons-auth-provider`.

---

### 2. What `@bri/addons-auth-provider`'s "Navigation Exclusion" Did
In earlier versions, when token validation failed, the auth provider would forcibly push or redirect the browser away (`router.push('/main-page?logout=true')` or `window.location.replace`). 

In `0.10.6-mfe`, that aggressive page navigation was **excluded/suppressed** so users wouldn't be booted off the current page when session expiration or MFA occurred.

---

### 3. Why `customAxios`'s 401 Handler is Still Essential
The 401 handler in [`services/custom-axios.ts`](file://~/Development/qcash-ui-dashboard/services/custom-axios.ts#L65) is actually the counterpart that makes the "no-navigation" UX work:

1. **Prevents Page Navigation**:
   Instead of redirecting to `/main-page`, when `newEventSessionExpired` is enabled, it returns a pending promise and dispatches `showDialog`.
2. **Holds the API in Queue**:
   It suspends the failed dashboard API calls (`queue.push({ resolve, reject })`).
3. **Triggers Re-Authentication**:
   The host listens for `showDialog`, pops up the in-place password/PIN modal, and refreshes the token.
4. **Retries the Request**:
   Once re-authenticated, the pending dashboard requests resolve seamlessly without page refresh or navigation.

> **Summary**: If we removed the 401 handler from `customAxios`, the app wouldn't navigate away, but all dashboard APIs (financial reports, account summary, transactions, forex) would immediately reject and fail with raw 401 errors, and the re-login popup would never trigger.
