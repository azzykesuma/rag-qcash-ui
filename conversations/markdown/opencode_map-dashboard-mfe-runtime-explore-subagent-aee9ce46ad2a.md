## 9. Confirmed risks versus version differences

### Confirmed code-level navigation/integration risks

1. **The exposed dashboard is not self-contained.** It requires a host-provided, shared auth context and router. Without one, guard rejects and the page remains in its default loading state.
2. **No host-router injection/fallback implementation exists.** The only router is standalone `next/router`; the documented `useAppRouter` arrangement is stale.
3. **Standalone auth destinations are absent locally.** Auth defaults to `/landing-page` and `/homepage`, while this app has only root and dashboard pages. Next’s router treats root-relative pushes as internal/base-path-aware navigation; absent external rewrites, those destinations resolve inside this app and have no matching page.
4. **Idle logout can trigger the same missing standalone destination** after 15 minutes.
5. **Runtime fallback is not a retry fallback.** Any existing host MF instance is trusted even if required remotes are unregistered.
6. **Raw dashboard CSS is host-dependent.** `./dashboard` does not load `./globals`; restoration cannot bootstrap CSS from nothing.
7. **Hardcoded HTTP remote entries** can be blocked as mixed content when consumed from an HTTPS host.

### Differences without evidence of a navigation defect

- Next 16 with React 18 is within Next’s declared peer range.
- Auth `0.9.142-mfe` with React 18.3 is within auth’s peer range.
- Rspack’s MF runtime `0.21.6` and enhanced runtime `2.8.0` coexist. This deserves integration testing, but no failure is demonstrated in this repository.
- `react-is` is 19.2.7 while React is 18.3.1; no routing code uses it directly.
- `requiredVersion: false` permits host version skew for shared packages. That is compatibility exposure, not proof of a current mismatch.
