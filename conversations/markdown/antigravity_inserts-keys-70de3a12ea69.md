        ('module.rcvOffUs', 'zh', 'RCV 跨行'),

        ('module.rcvOnUs', 'id', 'RCV On-us'),
        ('module.rcvOnUs', 'zh', 'RCV 本行')

INSERT INTO qcash_language.language_values (language_key_id, language_id, value, created_at, updated_at)
SELECT
    lk.id,
    l.id,
    tv.val,
    NOW(),
    NOW()
FROM target_values tv
JOIN qcash_language.language_keys lk ON lk."key" = tv.key_name
JOIN qcash_language.language_modules lm ON lm.id = lk.language_module_id AND lm.module_name = 'account-receivable'
JOIN qcash_language.languages l ON l.code = tv.lang_code
ON CONFLICT (language_key_id, language_id)
DO UPDATE SET
    value = EXCLUDED.value,
    updated_at = NOW();

COMMIT;

The keys in **Step 2** and **Step 3** are **completely different sets of keys**—none of the keys in Step 3 were inserted in Step 2.

Here is the difference and why Step 3 is needed:

---

### 1. Step 2 is for **Brand New Keys**
* **Target keys**: `error.internal`, `page.listMandate`, `data.all`, `data.mandateType.adhoc`, etc.
* **Database state**: These keys **never existed** in the `qcash_language.language_keys` table.
* **Action**: `CALL qcash_language.insert_language_key_with_values(...)` creates the key in `language_keys` **and** inserts all 3 language values in `language_values`.

---

### 2. Step 3 is for **Pre-Existing Keys** (Adding Chinese `zh` / Updating Values)
* **Target keys**: `data.batch.referenceNumber`, `form.mandate.type`, `modal.uploadMandate.onUs`, `module.rcvOnUs`, etc.
* **Database state**: These keys **already exist** in the database from previous releases (they already have `id` and `en` values).
* **Action**: In this task, you are adding the **new Chinese (`zh`) translation** or updating an existing label.

---

### Why Can't We Just Use Step 2 for Both?
According to the Confluence documentation:
> If a key already exists in `qcash_language.language_keys`, running `CALL qcash_language.insert_language_key_with_values(...)` will **fail with an exception**:
> `duplicate key value violates unique constraint`

**Step 3** handles this safely by:
1. Leaving the existing `language_keys` row intact.
2. Only updating or inserting the missing translations in `language_values` using `ON CONFLICT (...) DO UPDATE`.

Here is what is happening under the hood:

---

### 1. `p_value_id` is **Bahasa Indonesia**, NOT a Database ID
In the procedure parameter list:
- **`p_value_id`** $\rightarrow$ Value for **Bahasa Indonesia** (language code `'id'`), e.g. `'Mingguan'`.
- **`p_value_en`** $\rightarrow$ Value for **English** (language code `'en'`), e.g. `'Weekly'`.
- **`p_value_zh`** $\rightarrow$ Value for **Chinese** (language code `'zh'`), e.g. `'每周'`.

None of these are database primary keys; they are the actual translation strings (`TEXT`).

---

### 2. How the Integer IDs are Resolved Internally
You are completely right that the tables store integer foreign keys (`category_id`, `language_module_id`, `language_id`). 

The stored procedure was specifically created by the Language Management team so developers **do NOT need to manually look up or hardcode integer IDs**. 

Notice what happens inside the procedure body:

#### A. For `category_id` (Integer)
```sql
(SELECT id FROM qcash_language.categories WHERE name = p_category_name)
```
When you pass `'data'`, this subquery automatically converts `'data'` into its integer ID:
* As shown in your DBeaver screenshot of `categories`, `'data'` is automatically resolved to integer `15`!

#### B. For `language_module_id` (Integer)
```sql
(SELECT id FROM qcash_language.language_modules WHERE module_name = p_module_name)

When you pass `'account-receivable'`, it queries `language_modules` and resolves its integer ID (e.g. `19` or similar).

  ADHOC: "data.adhoc",

export const getMappedTranslationKey = (key: string): string => {
  return mapTranslate[key] ?? key;
};
```
* **Purpose**: Automatically maps raw backend enum values and legacy un-prefixed text strings to valid `{category}.{namaKey}` keys compliant with the database schema.

#### 2. Updated [`use-translate.ts`](file:///C:/Work/qcash-ui-account-receivable/hooks/use-translate.ts)
The translation lookup hook was modified in three ways:

1. **Automatic Key Interception**:
   ```ts
   const lookupKey = getMappedTranslationKey(key);
   ```
   Whenever a component calls `t("On Us")` or `t("Adhoc")`, the hook automatically intercepts it and converts it to `data.onUs` or `data.adhoc`. Existing UI code does not break even if it still uses legacy raw strings.

2. **Expanded Fallback Sources (`[tAR, tCommon]`)**:
   ```ts
   const isCommon = COMMON_PREFIXES.some((p) => lookupKey.startsWith(p));
   const sources = isCommon ? [tCommon, tAR] : [tAR, tCommon];
   ```
   - If a key starts with `action.`, `button.`, or `module.`, it checks `tCommon` first, then falls back to `tAR`.
   - For all other keys, it checks `tAR` first, but now also falls back to `tCommon` if not found in `tAR` (previously it only checked `[tAR]`).

3. **Normalized Local JSON Fallback**:
   ```ts
   const dict = LOCAL[i18n.language] ?? LOCAL["en"];
   return dict[lookupKey] ?? key;
   ```
   If the remote translation service has not returned the value yet, it falls back to the bundled local JSON using the normalized `lookupKey`.
