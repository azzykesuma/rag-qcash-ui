# Link to stale header navigation

There is a credible direct link.

Issuance performs all internal navigation through its own imported Next `Link`/`useRouter`, for example:

- `~/Development/qcash-ui-issuance-lc/containers/new-skin.tsx:8`
- `~/Development/qcash-ui-issuance-lc/containers/new-skin.tsx:65-77`
- `~/Development/qcash-ui-issuance-lc/containers/detail/view-new-skin.tsx:13`
- `~/Development/qcash-ui-issuance-lc/containers/detail/view-new-skin.tsx:268`
- `~/Development/qcash-ui-issuance-lc/containers/detail/view-new-skin.tsx:491`
- `~/Development/qcash-ui-issuance-lc/containers/detail/view-new-skin.tsx:650`

The host header derives active navigation/breadcrumb state from the host router’s pathname:

- `~/Development/qcash-ui-header-footer/layouts/default/container/breadcrumb/utils/useRouterPathV2.tsx:31-56`

Issuance and host have different Next versions, and issuance does not explicitly share `next` or `next/router`. If the exposed remote resolves a distinct router instance, its `router.push` or Link navigation can update URL/history without delivering the host router events that drive the header, leaving header navigation stale until reload.

The risk is increased by root-relative paths that know nothing about the shell’s `/v2` base path, while issuance’s standalone base path is `/issuance-lc-v2`:

- `~/Development/qcash-ui/next.config.js:69`
- `~/Development/qcash-ui-issuance-lc/next.config.js:64`

The header’s LC modal also mixes host `router.asPath`, manually inserted `/v2`, a federation-derived URL and both SPA/full-page navigation:

- `~/Development/qcash-ui-header-footer/layouts/default/container/menu/components/LcImportModal.tsx:97-113`

Therefore stale header state is not caused by a QUI visual component; it is linked to router ownership/base-path ambiguity at the shell–remote boundary. No test currently covers this path.
