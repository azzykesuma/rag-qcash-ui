Here is the exact breakdown of what the current `@bri/addons-auth-provider` (`0.10.7-mfe-test`) provides versus what was in this repository:

---

### What `@bri/addons-auth-provider` Already Provides

In `0.10.7-mfe-test` (`request-interceptors.js`), `createQcashAxios` **already includes native process ID generation and correlation**:

```js
// Inside @bri/addons-auth-provider request-interceptors:
if (!axiosConfig.url?.includes("cut-off")) {
  var processId =
    axiosConfig.headers.get("grpc-metadata-process_id")?.toString() ??
    createProcessId();

  axiosConfig.headers.set("grpc-metadata-process_id", processId);
  axiosConfig.processId = processId;
}
```

- **`grpc-metadata-process_id` (lowercase)**: **Provided natively.** It generates a UUID (via `crypto.randomUUID` with CryptoJS fallback) and sets the header.
- **`axiosConfig.processId`**: **Provided natively.** It sets `processId` directly on `axiosConfig`.
- **`Authorization: Bearer <token>`**: **Provided natively.** Reads from `localStorage["access-token"]`.

---

### Why Those Extra Properties Were Retained

There are two specific things `@bri/addons-auth-provider` **does not** do that were present in this repository's legacy code:

1. **`metadata.processId` nesting in `workflow.ts`**:
   - The provider sets `config.processId = processId` directly.
   - However, [services/workflow.ts](file:///C:/Work/qcash-ui-workflow/services/workflow.ts#L12) historically looked for a nested object:
     ```ts
     err.processId = response.config?.metadata?.processId || "";
     ```
   - If `config.metadata` is omitted without updating `workflow.ts`, `err.processId` would resolve to `""` during mutation assertions.

2. **`X-Lang` header**:
   - The provider **does not** inject `X-Lang`.
   - The original [services/custom-axios.ts](file:///C:/Work/qcash-ui-workflow/services/custom-axios.ts) sent `"X-Lang": localStorage.getItem("locale") || "id"` so backend services return validation and error messages localized in Indonesian (`id`) or English (`en`).

3. **Casing (`Grpc-Metadata-Process_id` vs `grpc-metadata-process_id`)**:
   - The provider sets the lowercase header `"grpc-metadata-process_id"`.
   - The legacy interceptor was setting both casings (`Grpc-Metadata-Process_id` and `grpc-metadata-process_id`) to accommodate legacy services reading plain object keys directly without case-folding.

---

### Can We Simplify and Remove the Extra Interceptor?

**Yes.** If you prefer the cleanest implementation with zero extra interceptors:
1. Update [services/workflow.ts](file:///C:/Work/qcash-ui-workflow/services/workflow.ts#L12) to read `response.config?.processId`:
   ```ts
   err.processId = response.config?.processId || response.config?.metadata?.processId || "";
   ```
2. Rely directly on `@bri/addons-auth-provider`'s native `grpc-metadata-process_id` and `processId`.

Would you like me to remove the manual `processId` interceptor and only keep `X-Lang` (or remove both if `X-Lang` is not strictly needed by your backend)?

### 1. The Interceptors

Interceptors act as middleware pipeline hooks that inspect or transform HTTP requests and responses. There are two layers active:

#### A. Global Interceptors (Provided by `@bri/addons-auth-provider`)
When you call `createQcashAxios()`, the provider automatically registers the following interceptors in exact order:

1. **Lazy `baseURL` Resolution (Request)**:
   - Resolves the API `baseURL` dynamically from `AuthProvider`’s `apiUrl` prop after mounting, falling back to `config.baseUrl`.
2. **Bearer Token & Tracing (Request)**:
   - Checks `localStorage["access-token"]` and attaches `Authorization: Bearer <token>`.
   - Generates a UUID and attaches the `grpc-metadata-process_id` header and `config.processId` (for all routes except cut-off).
3. **WAF Protection (Response)**:
   - Detects false-positive HTTP 200 responses where the body is HTML (`content-type: text/html`) generated by Web Application Firewalls (e.g., F5/Imperva blocks). It extracts the Support ID and converts it into a rejected error so it won't be parsed as JSON.
4. **Session & Auth Management (Response)**:
   - **401 on Root/Dashboard**: Automatically clears `localStorage` auth tokens and redirects to the landing page.
   - **401 / 499 on Sub-pages**: Prevents page crash by dispatching the global `showDialog` event (which shows the re-login popup), holds concurrent requests in a promise queue, and automatically replays all queued requests once the user re-authenticates.
   - **"Another Login Detected"**: Detects concurrent session invalidation and logs the user out.
   - **5xx Server Errors**: Dispatches `showServerError` with the `processId` for immediate error tracking modals.
   - **Network Timeout**: Catches missing responses and standardizes them as `504 Connection Timeout`.

#### B. Local Request Interceptor (Kept in `custom-axios.ts`)
```ts
customAxios.interceptors.request.use(
  (reqConfig: InternalAxiosRequestConfig) => {
    const locale = typeof window !== "undefined" ? localStorage.getItem("locale") || "id" : "id";
    if (reqConfig.headers && typeof reqConfig.headers.set === "function") {
      reqConfig.headers.set("X-Lang", locale);
    } else if (reqConfig.headers) {
      (reqConfig.headers as any)["X-Lang"] = locale;
    }
    return reqConfig;
  },
  (error: any) => Promise.reject(error)
);
```
- **Purpose**: Injects the `X-Lang` header (`"id"` or `"en"`) retrieved from `localStorage.getItem("locale")`.
- **Why**: QCash backend microservices inspect `X-Lang` on incoming requests to localize validation error messages, status descriptions, and notification strings in the user's preferred language.

### 2. `assertOk`

```ts
export function assertOk<T = any>(
  res: AxiosResponse<T & { error?: boolean; message?: string }>
): AxiosResponse<T> {
  if (res.status !== 200 || (res.data as any)?.error) {
    const msg = (res.data as any)?.message || "Server Error";
    throw new Error(msg);
  }
  return res as AxiosResponse<T>;
}
```

- **Purpose**: Guards against backend responses that return HTTP `200 OK` despite containing a business/domain error.
- **Why it's needed**:
  - By default, Axios only rejects promises for HTTP status codes outside the 2xx range (e.g., 4xx, 5xx).
  - Certain legacy or proxy endpoints in QCash return status `200 OK` with a payload like `{ error: true, message: "Invalid workflow step" }`.
  - Without `assertOk`, Axios would treat this as a successful response and run `.then()`.
  - `assertOk` checks both `res.status !== 200` and `res.data.error === true`. If either fails, it throws an `Error(message)`, immediately diverting execution to the `.catch()` block.
- **Usage example** (from [services/companies.ts](file:///C:/Work/qcash-ui-workflow/services/companies.ts#L7)):
  ```ts
  return customAxios.get(url).then(assertOk).then(pickData).catch(standardReject);
  ```

### 3. `standardReject`

```ts
export function standardReject(error: any) {
  const axiosErr = error as AxiosError;
  const errorData = axiosErr?.response?.data || { message: "Server Error" };
  const errorMessage =
    typeof errorData === "object" && errorData && "message" in errorData
      ? (errorData as any).message
      : "Server Error";
  const rejectedError = new Error(errorMessage);
  (rejectedError as any).processId =
    error?.processId ||
    (error?.response?.data as any)?.processId ||
    (error?.response?.data as any)?.processID ||
    "";
  return Promise.reject(rejectedError);
}
```

- **Purpose**: Normalizes Axios error objects into a lightweight, standard `Error` containing a clean error message and tracking `processId`.
- **Why it's needed**:
  - Raw `AxiosError` objects contain large circular structures (`request`, `response`, `config`).
  - React components, toasts, and UI error modals usually only need two pieces of data:
    1. A readable string message (`error.message`).
    2. The tracking ID (`error.processId`), so users can quote support IDs to helpdesk when reporting issues.
  - `standardReject` extracts the message from `response.data.message` and extracts the correlation ID across all common casing variants (`error.processId`, `response.data.processId`, `response.data.processID`), returning a clean rejected `Error` instance ready for consumption by React Query or UI handlers.

### Root Cause of the CORS Error

When running `qcash-ui` (host on `http://localhost:3000`) and `qcash-ui-workflow` (remote MFE on `http://localhost:3001`) locally, two distinct CORS barriers occurred:

1. **Remote Asset & Health Check Fetching (Host $\to$ Remote)**:
   - When `qcash-ui` loads `qcash-ui-workflow`'s `remoteEntry.js` or runs `urshifuPlugin` health checks (`fetch(remoteUrl, { method: "HEAD" })`), it performs cross-origin requests from port `3000` to port `3001`.
   - [next.config.js](file:///C:/Work/qcash-ui-workflow/next.config.js) previously lacked `async headers()`, returning no `Access-Control-Allow-Origin: *` and causing the browser to block chunk and script loading.

2. **Backend API Calls (Localhost $\to$ OCP Dev Backend)**:
   - In browser sessions on `localhost`, Axios requests with custom headers (`Authorization`, `grpc-metadata-process_id`, `X-Lang`) were dispatched directly to `http://internal-service.example.com/api`.
   - The remote backend gateway does not permit `http://localhost:3000` / `3001` or custom preflight headers, resulting in preflight `OPTIONS` failure.

---

### Implementation Details

Following the pattern implemented in `qcash-ui-livechat` and `qcash-ui-auto-collection-registration`, a local reverse proxy and permissive local CORS headers were established:

1. **Permissive CORS Headers & Next.js Reverse Proxy ([next.config.js](file:///C:/Work/qcash-ui-workflow/next.config.js#L20-L50))**:
   - **`headers()`**: Attached `Access-Control-Allow-Origin: *`, `Access-Control-Allow-Methods`, and `Access-Control-Allow-Headers` for `/:path*` so the host shell (`localhost:3000`) can load `remoteEntry.js` and all static chunks.
   - **`rewrites()`**: Configured `/api/:path*` and `/gym-api/:path*` rewrites with `basePath: false` to forward requests server-to-server to the OCP `gym-master` API gateway (server-to-server calls bypass browser CORS preflight entirely).

2. **Localhost Dev Proxy Bridge ([services/custom-axios.ts](file:///C:/Work/qcash-ui-workflow/services/custom-axios.ts#L25-L36))**:
   - In `development` mode on `localhost`, requests targeting `gym-master` are automatically routed through the local Next.js dev server proxy at `http://localhost:3001/api`.
   - Zero impact in production environments or when deployed to OCP.

3. **Type Compatibility Improvements**:
   - [services/custom-axios.ts](file:///C:/Work/qcash-ui-workflow/services/custom-axios.ts): Loosened interceptor and helper (`assertOk`, `pickData`, `pickDataWithPagination`) parameter signatures to `any` to prevent type mismatches across nested Axios versions.
   - [services/workflow-helpers.ts](file:///C:/Work/qcash-ui-workflow/services/workflow-helpers.ts): Updated `unwrapResponse` and `unwrapResponseOrThrow` signatures to accept `any`.
   - [services/workflow.ts](file:///C:/Work/qcash-ui-workflow/services/workflow.ts): Explicitly typed `getWorkflowTaskMeCreatedApprovedV3` as `Promise<any>`.
   - [services/downloads.ts](file:///C:/Work/qcash-ui-workflow/services/downloads.ts): Explicitly cast `content as string` for download handling.

### 🔍 Investigation: Root Cause of `[HostAuthGate] Failed to hydrate authentication`

The error shown in your console:
```text
▶ {error: {...}} host-console-events-document-start.js:1
▼ [HostAuthGate] Failed to hydrate authentication
  ▶ {message: 'Network Error', name: 'AxiosError', isAxiosError: true, code: 'ERR_NETWORK', config: {...}}
```

#### 1. Why It Happened
1. **Host Authentication Validation (`HostAuthGate`)**:
   - In [qcash-ui/components/providers/HostAuthGate.tsx](file:///C:/Work/qcash-ui/components/providers/HostAuthGate.tsx#L235-L254), on initial mount or token sync, it invokes `runGuard(currentBriAuth, "BRI")`, which executes `auth.guard()` from `@bri/addons-auth-provider`.
2. **Hardcoded Remote Destination in `@bri/addons-auth-provider`**:
   - Inside `@bri/addons-auth-provider`, its internal Axios instance resolves `baseURL` using its bundled `env.js`. In local development (`localhost`), it resolves to `http://internal-service.example.com/api`.
   - `auth.guard()` calls `authService.validateToken()` (`GET /auth/me`) and then `authService.validateMenu()` (`POST /menu/me`) with custom headers (`Authorization: Bearer <token>`, `X-Lang: en`, `Content-Type: application/json`).
3. **CORS Preflight Block (`ERR_NETWORK`)**:
   - Because the frontend runs at `http://localhost:3000` and the request destination is `http://internal-service.example.com/api/...`, the browser triggers an HTTP `OPTIONS` preflight request.
   - The remote gateway at `gym-master` does **not** allow cross-origin requests from `http://localhost:3000`.
   - The browser blocks the response completely. In Axios, browser-blocked CORS preflight failures manifest as `{ message: 'Network Error', name: 'AxiosError', code: 'ERR_NETWORK' }`.
   - `validateMenu()` rejects with this error, which bubbles up to `HostAuthGate` and triggers the fallback error screen ("Unable to verify your session").

---

### 🛠️ Solution Implemented

To bypass browser CORS restrictions locally without modifying remote backend gateways or needing Chrome flags (`--disable-web-security`), a 2-part reverse proxy was configured across **`qcash-ui`** and **`qcash-ui-workflow`**:

```
[Browser on localhost:3000]
        │
        │ 1. dev-proxy intercepts XMLHttpRequest / fetch
        │    Reroutes: gym-master.../api/... ──► /api/... (Same Origin)
        ▼
[Next.js Dev Server (localhost:3000)]
        │
        │ 2. next.config.js rewrites() forwards request (Server-to-Server)
        ▼
[Remote OCP Backend (gym-master)]
```

#### 1. Next.js Server-Side Reverse Proxy ([qcash-ui/next.config.js](file:///C:/Work/qcash-ui/next.config.js#L145-L179))

### 2. Root Cause: Why `task` & `count` Were Never Re-Executed

#### A. Host Shell Clobbers Multiple `showDialog` Events ([`qcash-ui/hooks/use-session-expiration.ts`](file:///C:/Work/qcash-ui/hooks/use-session-expiration.ts#L30-L38))

3. A few milliseconds later, `workflow` hits 401 on `12346130`. It also dispatches `showDialog` containing `{ resolve: resolve_WF, queue: [], url: "12346130" }`.
4. The Host Shell's listener runs again:
   ```typescript
   setPropsModal((prev) => ({
     show: true,

       ...value.detail, // ⚠️ OVERWRITES fund-transfer with workflow!
       shouldRefresh: value.detail.shouldRefresh || prev?.exception?.shouldRefresh,
   ```

   Notice that while `shouldRefresh` is combined with `||`, **`exception` (including `resolve` and `queue`) is completely overwritten!**

#### B. Per-MFE Isolated Queues in `@bri/addons-auth-provider` ([`create-axios.ts`](file:///C:/Work/addons-auth-provider/src/global-custom-axios/create-axios.ts#L87-L108))

### 3. Why Case B (Prerelease) Reloaded the Page

   ```typescript

   ```
   Because `shouldRefresh` used an `||` accumulator, `shouldRefresh: true` survived even when `exception` was overwritten!
4. On login completion, [`use-modal-session-expired.tsx`](file:///C:/Work/qcash-ui/hooks/use-modal-session-expired.tsx#L124-L129) saw `shouldRefresh: true` and executed:

### 4. How We Can Fix This

There are two viable fixes:

#### Option 1: Broadcast Session Renewal to All MFEs (Recommended & Cleanest)
Instead of relying on the Host Shell to hold an array of every MFE's `resolve` callback:
- When login succeeds, the host already broadcasts a custom event:
  `window.dispatchEvent(new CustomEvent("qc-bridge-sync", { detail: { source: "token-change" } }))`.
- In `@bri/addons-auth-provider`'s `attachAuthInterceptor`, listen to `qc-bridge-sync` (or a `session-renewed` window event). When received:
  - Every active `createQcashAxios` instance reads the new token from `localStorage` and immediately flushes its own queue (`state.flush(newToken)`) and retries its active request.
  - No MFE promise is dropped, regardless of how many MFEs hit 401 concurrently.

#### Option 2: Host Shell Queue Aggregation in `qcash-ui`
- In [`use-session-expiration.ts`](file:///C:/Work/qcash-ui/hooks/use-session-expiration.ts), collect incoming `showDialog` exceptions into an array (`exceptions: [...prev.exceptions, value.detail]`) rather than overwriting `exception`.
