# Investigation result

This is a Pages Router application. There is no `app/` or `src/app/` layout tree. The effective auth architecture mounts both auth packages for every route, but almost every host-side auth caller still consumes the Ordent context.

The most likely auth failure is:

1. On `/helpdesk`, `/plafon-pegadaian`, or `/systems`, the bridge selects BRI as soon as a token exists.
2. Only Ordent is hydrated with `guard()`.
3. Ordent-to-BRI replication is explicitly skipped on those BRI-preferring routes.
4. The currently installed BRI package does not expose most setters the bridge tries to call.
5. Therefore a BRI bridge snapshot can remain `username: "Guest"` and `isAuthoritiesReady: false` indefinitely unless an external remote calls BRI `guard()` itself.

There is also a Module Federation context-identity risk because both auth packages are shared without `singleton: true`.

## Bottom line

- The local host provider nesting is structurally correct: every page/layout remote is under both auth providers.
- Every direct host feature caller except the bridge uses Ordent.
- BRI is only consumed by the bridge and potentially by external remotes.
- BRI-preferring routes select a BRI context that the host itself never hydrates and explicitly refuses to synchronize on those routes.
- Context identity across remotes is not guaranteed because neither auth package is singleton.
- The current `node_modules` is stale relative to `package.json`/`yarn.lock`, so local behavior and bridge version diagnostics do not represent a clean committed install.
- Remote-specific auth ownership cannot be proven from this repository; only a running share-scope inspection or the remote repositories can establish it.
