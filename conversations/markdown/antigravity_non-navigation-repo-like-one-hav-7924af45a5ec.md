## Turn 95: Assistant

`useMfeRouterSync` was introduced as a **client-side polling workaround (band-aid)** to compensate for how Module Federation breaks Next.js routing in QCash.

Here is why it was created and what problems it was attempting to solve:

---

### 1. `next/router` Context Is Decoupled Between Host and Remote
* **Host shell ([`qcash-ui`](file:///C:/Work/qcash-ui)):** Runs **Next.js 13.5.11**.
* **This remote repo ([`qcash-ui-global-internal-transfer`](file:///C:/Work/qcash-ui-global-internal-transfer)):** Runs **Next.js 14.2.4**.

Next.js routing relies on React Context (`RouterContext`). Because Next 13 and Next 14 cannot share a single router context instance across Module Federation boundaries:
* When a remote component or federated header/footer calls `router.push('/...')`, it only executes `window.history.pushState()` in the browser.
* The **host shell router is never notified**. It does not re-render the page or switch remote entry points.
* The browser address bar updates, but the page stays frozen on the old view.

---

### 2. Browser `pushState()` Dispatches No Native Events
Normally in a React app, route transitions are captured via `router.events` or `popstate`:
* **`router.events`** in the remote does not fire when the shell or header-footer navigates.
* **`window.addEventListener('popstate')`** only fires on browser Back/Forward button clicks—it does **not** fire on programmatic `history.pushState()` calls.

Because there is no native DOM event when another remote (like `header-footer`) calls `pushState()`, the developers used a **100ms `setInterval`** to poll `window.location.pathname` and detect when the URL changed under their feet.

---

### 3. Crossing MFE Boundaries Within This Repository
In `qcash-ui` (host shell), several distinct Next.js pages host components from this repo and external repos:
* `/v2/global/internal-transfer` (Internal Transfer)
* `/v2/global/mass-transaction/...` (Mass Transaction)
* `/v2/global/external-transfer/...` (Hosted by an entirely different MFE: `qcash-ui-external-transfer`)
* `/v2/global/internal-transfer/transaction-list` (Separate Next page in shell)

When switching between these features (e.g. going from Internal Transfer to Mass Transaction, or jumping from `transaction-list` back to root), soft navigation hung. To unstick it, the developers added `useMfeRouterSync` to detect those specific transitions and force `window.location.href = ...` (a hard document reload).

---

### Summary: Is it an architectural code smell?
**Yes.** `useMfeRouterSync` exists solely because:
1. **The host shell and remotes have incompatible Next.js versions (Next 13 vs 14).**
2. **The shell/header-footer does not own or coordinate navigation across MFE boundaries.**

If [`qcash-ui-header-footer`](file:///C:/Work/qcash-ui-header-footer) or the host shell forced hard document navigation whenever navigating between different micro-frontend routes (just as was done for `/v2/import-lc/issuance-lc`), this polling hook would not be necessary at all.

## Turn 97: Assistant

The short answer is **no, you do not have to upgrade all remotes in lockstep**, but **upgrading Next.js alone will not automatically fix cross-MFE routing**.

Here is why, along with the architectural reality of QCash's Module Federation:

---

### 1. The Independent Release Cadence (The Purpose of MFEs)
QCash has over 50 micro-frontend repositories maintained by different squads. 
* If updating the host shell required every remote to upgrade immediately, you would lose the core benefit of micro-frontends: **independent deployments and upgrade cadences**.
* Module Federation allows remotes running different minor versions to coexist, provided core singletons (`react`, `react-dom`) remain compatible (e.g. React 18).

---

### 2. Upgrading Next.js Does Not Automatically Solve Router Sharing
Even if the host shell and all remotes were on the **exact same version of Next.js** (e.g., all on Next 14.2), Next.js Pages router (`next/router`) is **fundamentally not designed to be federated as a shared singleton**.

* **Why?** Each Next.js build creates its own internal route manifest, build ID, and page chunk loader.
* When a remote calls `router.push("/some-page")`, that router only understands routes declared inside *its own* build manifest—it does not know how to dynamically instruct the host shell's router to unmount remote A and mount remote B.
* Trying to force `next/router` as a shared singleton across remotes frequently causes chunk load failures, runtime errors, and route tree collisions.

---

### 3. How Navigation Should Actually Be Architected Across MFEs

Instead of requiring lock-step framework upgrades across all repositories, there are two industry-standard patterns:

#### Pattern A: Boundary-Based Document Navigation (Recommended & Simplest)
* **Inside an MFE:** Use soft navigation (`router.push`) for pages within the same module.
* **Leaving an MFE:** Use standard document navigation (`window.location.href = targetUrl`).
  * When moving between micro-frontends (e.g., from *Internal Transfer* to *Dashboard* or *LC*), a full document load ensures:
    * React component trees, old stores, and memory are completely cleaned up.
    * Different Next.js/Webpack runtimes between remotes never conflict.
    * No reliance on polling hooks like `useMfeRouterSync`.

#### Pattern B: Shell-Delegated Navigation Event
Instead of `header-footer` or remotes invoking `router.push()` directly:
1. The remote dispatches a browser event:
   ```typescript
   window.dispatchEvent(new CustomEvent("qcash:navigate", { detail: { href } }));
   ```
