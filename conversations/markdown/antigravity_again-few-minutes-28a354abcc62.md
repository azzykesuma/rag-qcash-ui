Based on the investigation across [**`qcash-ui-forex`**](file:///D:/work/qcash-ui-forex) and [**`qcash-ui`**](file:///D:/work/qcash-ui), here is the detailed root cause analysis and how to resolve the issue.

---

### 1. Where Does the Error Message Come From & Why Does It Take Too Long?

1. **Origin of Error Screen**:
   The error message:
   > *"Feature temporarily unavailable — Sorry — this feature is temporarily unavailable. Please try again in a few minutes..."*
   
   originates from [`fallbackPlugin.tsx`](file:///D:/work/qcash-ui/services/federation/fallbackPlugin.tsx#L85-L103) in the host shell application ([**`qcash-ui`**](file:///D:/work/qcash-ui)).

2. **Why Loading Takes So Long (~15–20 seconds)**:
   In [`init.ts`](file:///D:/work/qcash-ui/services/federation/init.ts#L52-L61), `qcash-ui` registers the `RetryPlugin` for Module Federation:
   ```ts
   RetryPlugin({
     script: {
       retryTimes: 3,
       retryDelay: 5000, // 5 seconds per retry
       ...
     }
   })
   ```
   When the remote entry (`remoteEntry.js`) fails to respond or times out, `qcash-ui` retries 3 times with a 5-second backoff delay before eventually falling back to the `ErrorAlert` screen.

---

### 2. Root Cause Analysis

#### A. When Running in the App (Deployed / Remote Dev Environment)
* In [`registry.ts`](file:///D:/work/qcash-ui/constants/features/registry.ts#L649-L654), `qcash_ui_foreign_exchange` points to:
  ```ts
  customEntry: remoteEntry("foreign-exchange-v2")
  // Resolves to: http://internal-service.example.com/foreign-exchange-v2/_next/static/chunks/remoteEntry.js
  ```
* **Issue**: The `foreign-exchange-v2` service is currently **not deployed or unreachable** on `internal-service.example.com`. Because the server does not respond, the browser request hangs, hits the timeout, retries 3 times, and fails with the fallback screen.

---

#### B. When Running Locally with `qcash-ui` (Host Shell)
* **Issue 1: Missing Local Dev Port in `qcash-ui`**:
  [`registry-dev.ts`](file:///D:/work/qcash-ui/constants/features/registry-dev.ts#L6-L13) is currently empty:
  ```ts
  export const localDevPorts: Partial<Record<featureName, number>> = {
    // Missing: "qcash_ui_foreign_exchange": 3001
  };
  ```
  Because `qcash_ui_foreign_exchange` is not mapped to port `3001`, `qcash-ui` ignores your local server and tries to load from the remote dev server (`gym-master...`), which times out.

* **Issue 2: Missing `library: { type: "global", name: "..." }` in `next.config.ts`**:
  In [`next.config.ts`](file:///D:/work/qcash-ui-forex/next.config.ts#L43-L64), `ModuleFederationPluginV1` is missing the `library` export definition.
  Compare with other working Rspack MFEs (like `qcash-ui-dashboard-auto-collection`):
  ```ts
  new ModuleFederationPluginV1({
    name: "qcash_ui_foreign_exchange",
    filename: "static/chunks/remoteEntry.js",
    library: { type: "global", name: "qcash_ui_foreign_exchange" }, // <-- Required for browser global container attachment
    ...
  })
  ```

---

#### C. When Running `qcash-ui-forex` Standalone (Local Port 3001)
* **Hardcoded Design System (`qui`) Endpoint**:
  In [`federation.ts`](file:///D:/work/qcash-ui-forex/src/utils/federation.ts#L32), the standalone runtime fallback hardcodes:
  ```ts
  entry: "http://localhost:3000/design-system/static/remoteEntry.js"
  ```
  If you only run `qcash-ui-forex` without running `qcash-ui` on port 3000 (or if port 3000 is not serving the design system proxy), any QUI component (`Button`, `DataTable`, `QuiProvider`, etc.) in [`src/components/ui/index.tsx`](file:///D:/work/qcash-ui-forex/src/components/ui/index.tsx) fails to load `qui/components/*`.

---

### 3. Recommended Fixes

1. **Map Local Dev Port in `qcash-ui`**:
   In [`qcash-ui/constants/features/registry-dev.ts`](file:///D:/work/qcash-ui/constants/features/registry-dev.ts), add:
   ```ts
   export const localDevPorts: Partial<Record<featureName, number>> = {
     "qcash_ui_foreign_exchange": 3001,
   };
   ```
   *(Or open `qcash-ui` and configure the port override in MFE DevTools).*

2. **Add `library` Definition in `qcash-ui-forex/next.config.ts`**:
   In [`next.config.ts`](file:///D:/work/qcash-ui-forex/next.config.ts#L43), add `library: { type: "global", name: "qcash_ui_foreign_exchange" }`:
   ```ts
   new ModuleFederationPluginV1({
     name: "qcash_ui_foreign_exchange",
     filename: "static/chunks/remoteEntry.js",
     library: { type: "global", name: "qcash_ui_foreign_exchange" },
     remotes: {
       qui: "qui@http://internal-service.example.com/design-system/static/remoteEntry.js",
     },
     ...
   })
   ```

3. **Fallback URL for QUI Design System in `qcash-ui-forex/src/utils/federation.ts`**:
   Use the deployed design system entry or environment variable rather than hardcoding `localhost:3000`:
   ```ts
   remotes: [
     {
       name: "qui",
       entry: process.env.NEXT_PUBLIC_DESIGN_SYSTEM_URL || "http://internal-service.example.com/design-system/static/remoteEntry.js",
     },
   ],
   ```

### Key Findings & Root Cause

#### 1. Severe Latency & 504 Gateway Timeouts on the `foreign-exchange-v2` Pod
We benchmarked response times for remote entries and endpoints across different MFEs from inside the browser session:

| Endpoint / MFE | Status | Response Time |
| :--- | :--- | :--- |
| **`header-footer`** `remoteEntry.js` | `200 OK` | **47 ms** |
| **`global-component`** `remoteEntry.js` | `200 OK` | **100 ms** |
| **`design-system`** `remoteEntry.js` | `200 OK` | **133 ms** |
| **`foreign-exchange-v2`** `remoteEntry.js` | `200 OK` | **5,141 ms – 25,803 ms (5s to 26s)** |
| **`foreign-exchange-v2`** `/health` | **`504 Gateway Timeout`** | **30,017 ms (30s timeout)** |

#### 2. Host Module Federation 15-Second Timeout Trigger
In [`qcash-ui`](file:///D:/work/qcash-ui), Module Federation has a default **15,000 ms (15s)** timeout. 

When loading `/v2/foreign-exchange/dashboard`:
1. `qcash-ui` requests `http://internal-service.example.com/foreign-exchange-v2/_next/static/chunks/remoteEntry.js` and its dependent chunk `lib-b23869570571bc5f.js`.
2. Because the `foreign-exchange-v2` pod takes **15s – 26s+** to serve the static chunk (or hangs), the host loader exceeds its 15s limit:
   ```
   [MFE] Failed qcash_ui_foreign_exchange - module in 14994ms
   [RemoteErrorBoundary] Error: Module load timed out after 15000ms: qcash_ui_foreign_exchange
   ```
3. The host application catches the timeout via [`fallbackPlugin.tsx`](file:///D:/work/qcash-ui/services/federation/fallbackPlugin.tsx#L85-L103) and displays:
   > **"Feature temporarily unavailable"**  
   > *"Sorry — this feature is temporarily unavailable. Please try again in a few minutes..."*

---

### What Needs to Be Checked on the Pod / Deployment:

1. **Pod Resource Throttling / Event Loop Blocked**:
   * The `/health` endpoint times out with `504 Gateway Timeout` after 30s. The Node.js process inside the pod may be under heavy CPU/memory throttling or having an unhandled blocking operation.
   * Check pod logs in OpenShift / Kubernetes:
     ```sh
     oc logs -n <namespace> <forex-pod-name>
     oc describe pod <forex-pod-name>
     ```
2. **Static Asset Serving Architecture**:
   * If static assets (`/_next/static/chunks/*`) are served directly through Next.js Node process rather than an Nginx reverse proxy / cache, any Node event loop stall blocks static asset requests.

---
