## Concrete Plafon-only risk differences

### 1. Full-document reload actions can genuinely remount `HostAuthGate`

Plafon’s create/edit/view error paths offer `router.reload()`:

- `D:\work\qcash-ui-plafon-pegadaian\pages\plafon-pegadaian\create\index.tsx:56-65`
- `D:\work\qcash-ui-plafon-pegadaian\pages\plafon-pegadaian\edit\[id]\index.tsx:39-48`
- `D:\work\qcash-ui-plafon-pegadaian\pages\plafon-pegadaian\view\[id]\index.tsx:40-49`

None of the selected comparison MFEs uses `router.reload()` in exposed route code.

A reload destroys the entire document, including:

- Host `BriProviders`
- `HostAuthGate`
- its React refs and local state

The window-level guard record also disappears, so the new page executes the Host guard again. This is the clearest route behavior capable of an actual HostAuthGate unmount/remount. It is user-triggered rather than automatic, unless another component programmatically invokes the error action.

The reload behavior predates migration and is attributed to `ef7e25a6`.

### 2. Plafon retains a bespoke relogin/401 feedback path

Plafon alone has this combination:

1. It subscribes separately to the shared auth token:

   `D:\work\qcash-ui-plafon-pegadaian\containers\index.tsx:42-47`

2. Every post-mount token change triggers another activity-log request:

   `D:\work\qcash-ui-plafon-pegadaian\containers\index.tsx:69-84`

3. That activity request opts into `fallbackOnUnauthorized`:

   `D:\work\qcash-ui-plafon-pegadaian\services\plafon-pegadaian.ts:247-273`

In auth-provider 0.10.6, a fallback 401 still dispatches `showDialog`; it only returns fallback data immediately:

- `D:\work\qcash-ui\node_modules\@bri\addons-auth-provider\dist\src\global-custom-axios\interceptors\auth-interceptors.js:207-222`

The Host listens for that event and exposes children while relogin is pending:

- `D:\work\qcash-ui\components\providers\HostAuthGate.tsx:152-161`
- `D:\work\qcash-ui\components\providers\HostAuthGate.tsx:272-274`

When relogin rotates the access token, `HostAuthGate` observes `briAuth.token`, detects that the global validation record belongs to the previous token, and calls `guard()` for the new token:

- validated-token short circuit: `HostAuthGate.tsx:200-217`
- actual guard invocation: `HostAuthGate.tsx:223-248`
- dependencies include `briAuth.token`: `HostAuthGate.tsx:249`

Therefore the plausible loop is:

`Plafon request 401 → showDialog/relogin → token changes → Host guard executes for new token → Plafon token effect reloads activity logs → another 401 → repeat`

The selected comparison pages do not have this paired “token change → immediate fallback-on-401 request” mechanism.

Origins:

- `488a6943` introduced `createQcashAxios` and `fallbackOnUnauthorized`.
- `4e084525` introduced the token-change reload effect.
- These bespoke July migration accommodations were not removed by August’s centralized-guard patch.

This is the strongest explanation for repeated guard executions without HostAuthGate itself remounting.

### 3. Create-page request is not gated by authority readiness

Plafon create fetches account data whenever only `token && companyID` are truthy:

- `D:\work\qcash-ui-plafon-pegadaian\pages\plafon-pegadaian\create\index.tsx:44-48`

Rendering is gated later by `isAuthoritiesReady` at lines `52-84`.

Normally the Host gate prevents the remote from mounting before authorities are ready. During `sessionDialogPending`, however, HostAuthGate deliberately keeps children mounted. A token/company transition can consequently launch this request while centralized validation is changing state. A 401 then re-enters the shared dialog flow.

Approval Signature’s create route performs no pre-readiness API request:

- `D:\work\qcash-ui-approval-signature\pages\approval-signature\create\index.tsx:21-41`

Auto Collection similarly blocks on auth state before rendering its container:

- `D:\work\qcash-ui-auto-collection-registration\src\pages\registration\create\index.tsx:15-32`

### 4. Residual stale-user migration code remains, but is currently inert

Plafon still reads and derives old cross-user cache state:

- `D:\work\qcash-ui-plafon-pegadaian\pages\plafon-pegadaian\index.tsx:28-31`

`isStaleCache` is unused. Commit `b93d3391` originally paired these values with:

- `window.location.reload()`
- `session-user-data` removal
- an additional dependency-driven `guard()`
- a second mount-only `guard()`

Commit `68828c4a` removed both guard effects and the reload effect but left the variables. They cannot currently cause a reload or guard call, though they document that Plafon had a unique auth-persistence workaround not present in the bulk-migrated peers.

## Route-remount conclusion

Normal Plafon client-side navigation does not appear capable of remounting `HostAuthGate`:

- Host Plafon routes use module-level `next/dynamic` components and `router.push`, just like Account Statement and Approval Signature:
  - `D:\work\qcash-ui\pages\plafon-pegadaian\index.tsx:9-26`
  - `D:\work\qcash-ui\pages\plafon-pegadaian\create\index.tsx:9-26`
  - comparison: `D:\work\qcash-ui\pages\account-statement\index.tsx:9-26`

- `HostAuthGate` is outside `getLayout` and the routed component:
  - `D:\work\qcash-ui\pages\_app.tsx:177-206`

- A route change reruns the Host gate effect because `currentPath` changes, but the same-token validated record short-circuits before `runGuard()`:
  - `D:\work\qcash-ui\components\providers\HostAuthGate.tsx:200-205`

Thus:

1. **Actual HostAuthGate remount:** primarily Plafon’s hard `router.reload()` paths.
2. **Repeated guard without remount:** most plausibly token rotation driven by the Plafon-specific fallback-401/relogin/token-refetch cycle.
3. **Not supported by evidence:** duplicate 0.10.6 lock artifacts, missing auth singleton declaration, a different `_app` wrapper, or ordinary client-side route transitions.
