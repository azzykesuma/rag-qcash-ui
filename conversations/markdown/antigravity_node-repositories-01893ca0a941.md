### 1. Security Advisory Summary
The October security release addresses **10 vulnerabilities** (highest severity: **High**):
* **Flagship Vulnerability (`CVE-2026-111497`, High Severity):** Out-of-bounds write / memory corruption in Node's bundled **Brotli decoder**.

  * **Vector:** Node triggers this code whenever it decompresses Brotli data—either explicitly via `node:zlib` or **implicitly when applications invoke native `fetch()` on an upstream response compressed with Brotli (`Content-Encoding: br`)**.
* **Other CVEs:** TLS hostname verification bypasses (`CVE-2026-105481`–`CVE-2026-105483`), `c-ares` DNS flaws, and HTTP parsing issues (`CVE-2026-106069`–`CVE-2026-106074`).

## Turn 72: Assistant

That is a very common point of confusion with the official Node.js security advisories! 

The reason **Node 18 is not listed in the table** is because of how the Node.js project handles **End-of-Life (EOL)** versions:

---

### 1. The Official Node.js Security Policy
In every security release, the Node.js team **only tests, documents, and provides patch releases for supported release lines** (Active LTS and Maintenance LTS). 

Official Node.js security releases include this policy notice:
> *"It's important to note that End-of-Life versions are always affected when a security release occurs. However, because EOL lines no longer receive updates, no testing, backports, or patched binaries are produced for them."*

Node 18 reached official **End-of-Life (EOL) on April 30, 2025**. Because it is dead upstream:
* The Node.js security team does not backport fixes to it.
* They do not generate patch binaries (like `18.x.x`).
* They do not list it in the "Affected / Patched Versions" matrix because there is no patched version to recommend.

---

### 2. Does Node 18 Actually Contain the Vulnerability?
**Yes, absolutely.**

* **Brotli Decoder (`CVE-2026-111497`):** Node.js has bundled the Brotli compression engine directly into its C/C++ core since **Node.js v11.7.0**. Because Node 18 contains an older version of this bundled Brotli library, the out-of-bounds write flaw exists in Node 18 just as it did in Node 22 and 24.
* **TLS & `c-ares` DNS flaws:** Node 18 ships with older, frozen versions of `c-ares` and OpenSSL/TLS that contain these exact underlying issues.

---

### 3. Why This Creates a "False Sense of Security"

| What it Looks Like on the Blog | What it Actually Means |
| :--- | :--- |
| The table only lists **Node 22**, **Node 24**, and **Node 26**. | Node 22, 24, and 26 are the **only versions being fixed and supported**. |
| **Node 18 is missing from the list.** | Node 18 is **unsupported and permanently unpatched**. |

### Bottom Line
Being omitted from the blog's patch table does **not** mean Node 18 is immune—it means **the Node.js team has stopped fixing bugs for it**. 

Those 21 repositories running `node:18-alpine` are vulnerable to the Brotli issue and all other CVEs discovered since April 2025, and the only way to resolve them is upgrading the base image in their Dockerfiles to **`node:22-alpine`**.

Based on historical investigations retrieved from the **LLM Context Vault** and a code scan across the repositories under `C:\Work`, here is the complete analysis of why users get redirected back to `/main-page` instead of `/landing-page`, along with the list of **89 repositories** containing this redirect logic.

### 1. Root Causes (Vault & Code Analysis)

The system-wide redirection to `/main-page` instead of `/landing-page` is driven by **4 primary mechanisms**:

#### A. Header Avatar Logout & Session Timeout ([`qcash-ui-header-footer`](file:///C:/work/qcash-ui-header-footer/layouts/default/container/header/components/ListItem.tsx#L76))
* In `ListItem.tsx`:
  ```ts
  const newQlola = sessionStorage.getItem("new-qlola-flag");
  const destination = newQlola === "true" ? "/landing-page" : "/main-page";
  logout(destination);
  ```
* **Trigger:** If `new-qlola-flag` in `sessionStorage` is missing, cleared, `false`, or lost across cross-origin/incognito tabs, clicking the user avatar's **Logout** button automatically falls back to `/main-page`.
* Idle session expiration timers in the header also call `logout("/main-page")`.

#### B. Boilerplate Axios Interceptors across 80+ MFEs (`services/custom-axios.ts`)
Almost every micro-frontend repo contains legacy boilerplate in its Axios response interceptor:
* **401 Unauthorized at `/` or `/homepage`:**
  ```ts
  if ((isDashboard || isRoot) && error?.response?.status === 401) {
    localStorage.removeItem("access-token");
    window.location.replace("/main-page");
  }
  ```
* **"Another Login Detected" (Concurrent Login / Revoked Session):**
  ```ts
  if (error?.response?.data?.message === "Another Login Detected") {
    localStorage.removeItem("access-token");
    window.location.href = "/main-page?logout=true";
  }
  ```
* **Token Refresh Failure:** When refreshing the token returns a 401/403, the interceptor redirects to `/main-page?logout=true`.
* **Why it redirects to `main-page`:** When QCash introduced `/landing-page` (the modern QLola portal), the distributed Axios boilerplate across the individual MFE repositories was never updated.

#### C. Legacy Auth Provider (`@ordentco/addons-auth-provider`)
* In versions prior to the unified auth provider migration, the default `loginRoute` fallback in the provider is hardcoded to `/main-page`.
* During page navigation, if `guard()` or `validateToken()` fails, it calls:
  ```ts
  router?.push(`${loginRoute}?logout=true`);
  ```
  which pushes the user to `/main-page`.

#### D. Host Shell Fallback ([`qcash-ui`](file:///C:/work/qcash-ui/pages/main-page/index.tsx))
* In the host orchestrator (`qcash-ui`), if the feature toggle `toggleRedirectLandingPage` evaluates to `false`, it renders the legacy `main-page` instead of redirecting the user forward to `/landing-page`.
