### Explanation: Why the Type Fix Does Not Affect Style Variants

---

### 1. Root Cause of the Type Error

The error:
```text
Type error: Type '{ children: Element; variant: string; className: string; }' is not assignable to type 'IntrinsicAttributes & ContainerProps'.
Property 'variant' does not exist on type 'IntrinsicAttributes & ContainerProps'.

  273 |     return (
  274 |       <div className="usm-fixed usm-bottom-8 usm-left-0 usm-w-full usm-px-[3.3%]">
> 275 |         <Container variant="qcash" className="usm-shadow">
      |                    ^
```

* **Compile-Time Issue (TypeScript Type Checking)**: 
  * In the local codebase, `Container` is dynamically imported from Module Federation (`qcash-global-component/container`).
  * The local type definition (`ContainerProps` / `ContainerComponentType`) was statically defined with standard React HTML attributes without extending `VariantProps<typeof containerVariants>`.
  * Because TypeScript could not find `variant` declared in the local type definition during `next build` type checking (`tsc`), it threw a compile error and blocked the build.

---

### 2. Why the Runtime Style Variant Remains 100% Intact

The style variant and styling behavior are **unaffected** because:

1. **Remote Execution at Runtime**:
   * Under Module Federation, `Container` is resolved and executed at runtime from the remote bundle (`qcash-global-component`).
   * The actual implementation in `qcash-global-component` always expects and processes the `variant` prop using `class-variance-authority` (CVA):
     ```tsx
     export function Container({ className, children, customClassName, variant, ...props }: ContainerProps) {
       return (
         <div className={cn(containerVariants({ variant }), className)} {...props}>
           {children}
         </div>
       );
     }
     ```
2. **Prop Forwarding Unchanged**:
   * The JSX in [`containers/create/index.tsx`](file://~/Development/qcash-ui-user-manual/containers/create/index.tsx#L275) and [`containers/edit/index.tsx`](file://~/Development/qcash-ui-user-manual/containers/edit/index.tsx#L443) continues to pass `variant="qcash"` and `className="usm-shadow"`:
     ```tsx
     <Container variant="qcash" className="usm-shadow">
     ```
   * At runtime in the browser, `variant="qcash"` is passed directly into `containerVariants`, producing the exact same classes and layout styling as intended.

3. **Type-Only Correction**:
   * Pointing the type definition to `typeof import("@/@mf-types/qcash-global-component/container").default` in [`components/global/index.ts`](file://~/Development/qcash-ui-user-manual/components/global/index.ts#L75-L77) accurately mirrors the remote component's contract (`variant?: "default" | "qcash"`).
   * This satisfies TypeScript's type checker at build time **without modifying the rendered DOM structure, JS execution flow, or CSS styles**.

You don't see the conflict automatically when simply switching to `v0.0.1-release` on your local machine because of how Git operates:

---

### 1. Why Git Doesn't Show Conflicts Just by Checking Out a Branch
* A Git branch is just a standalone pointer to a specific commit. 
* Simply running `git checkout v0.0.1-release` or `git status` only shows the files in their current state on that branch. **Git will never show conflict markers unless you actively trigger a merge or rebase operation.**

---

### 2. Why Bitbucket Shows a Conflict While Local Doesn't
* **Bitbucket**: When you open a Pull Request (e.g. `v0.0.1-release` $\rightarrow$ `prerelease`), Bitbucket simulates `git merge origin/prerelease` on the server in the background. If both branches modified the same lines in `Dockerfile`, Bitbucket displays a **"Conflict"** banner on the PR UI.
* **Local**: To reproduce and trigger the exact same conflict on your local machine, you must explicitly run the merge command:
  ```bash
  git checkout v0.0.1-release    # or fix-auth-guard
  git fetch origin
  git merge origin/prerelease    # <-- This triggers the conflict locally!
  ```
  Once you execute this command, Git will output `CONFLICT (content): Merge conflict in Dockerfile`, and you will see the `<<<<<<< HEAD` / `>>>>>>>` markers in your editor.

---

### 3. Current Status in [`qcash-ui-livechat`](file://~/Development/qcash-ui-livechat)

```text
  ➔ @module-federation/nextjs-mf (v8.2.5)

```

  `require("webpack/lib/util/create-schema-validation")`

#### 2. What Changed in Webpack `5.10x`+
- In recent Webpack releases (like `5.110.3`), Webpack core maintainers refactored their internal file structure and **deleted `create-schema-validation` from `webpack/lib/util/`**.
- In **Webpack `5.93.0`** (and older `5.9x` versions), `create-schema-validation` is still present in that exact path.

#### 3. Why `NEXT_PRIVATE_LOCAL_WEBPACK=true` Triggers It
- By default, Next.js packages its own internal bundled version of Webpack.
- However, for Module Federation to work between micro-frontends, Next.js is configured with `NEXT_PRIVATE_LOCAL_WEBPACK=true` to use the `webpack` installed in `node_modules`.
- Because `yarn.lock` had `webpack: ^5.90.3`, `yarn install` resolved to the latest `5.110.3`, which instantly broke the Module Federation plugin.

### Why `subscription-management` only needed changes in `yarn.lock`

#### 1. How Yarn Dependency Locking Works
In both repositories, `package.json` had:
```json
"webpack": "^5.90.3"
```
The `^` (caret) means: *"Install any compatible version >= 5.90.3 and < 6.0.0"*.
- When `yarn.lock` already has an entry for `webpack@^5.90.3: version "5.93.0"`, running `yarn install` **reuses that exact locked version (`5.93.0`)** and will **never** upgrade it on its own.

---

#### 2. What happened in `subscription-management`:
- When fixing the race condition and adding dependencies in `subscription-management`, only individual packages (e.g. `axios`, `form-data`, `es-set-tostringtag`) were modified in `yarn.lock`.
- The existing locked entry for `webpack` was **preserved at `5.93.0`** in `yarn.lock`.
- Because `5.93.0` was never upgraded, `subscription-management` never hit the Webpack `5.110.3` breaking change.

---

#### 3. What happened in `qcash-ui-liquidities`:
- In PR #206 (`chore: update yarn.lock dependencies`), an automated or full `yarn upgrade` was run across the whole repository.
- This forced Yarn to re-resolve `webpack@^5.90.3` to the newest version available on the registry: **`5.110.3`**.
- Once `yarn.lock` recorded `5.110.3`, every build (local and Bamboo) began installing `5.110.3`, triggering the missing `create-schema-validation` error.

---

#### 4. The Two Ways to Fix:
1. **Option 1 (Only change `yarn.lock`)**: Revert the `webpack@^5.90.3:` entry in `liquidities/yarn.lock` back to version `5.93.0` (just like `subscription-management`).
2. **Option 2 (Pin in `package.json`)**: Change `"webpack": "^5.90.3"` to `"webpack": "5.93.0"` (or add `resolutions`). This prevents future `yarn upgrade` or lockfile updates from accidentally breaking it again.
