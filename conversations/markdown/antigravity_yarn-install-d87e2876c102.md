### Why This Happens

1. **Origin Mismatch**: The frontend is running on `http://localhost:3000`, making direct browser requests to `http://internal-service.example.com/api`.
2. **Missing Preflight Header**: Axios / the remote module attaches the custom header `x-process-id`. The browser initiates a preflight `OPTIONS` request, and the remote OCP gateway does not include `x-process-id` in its `Access-Control-Allow-Headers` response for `localhost`.

---

### Solution 1: Run Chrome with Web Security Disabled (Quickest for Local Dev)

Because this is an internal backend environment without wildcard CORS headers for localhost, the standard workflow for local development is to run a separate Chrome dev profile with CORS checks disabled:

Run this in PowerShell:

```powershell
& "C:\Program Files\Google\Chrome\Application\chrome.exe" --disable-web-security --user-data-dir="C:\tmp\chrome_dev" http://localhost:3000/v2/landing-page
```

*(Alternatively, you can install a browser extension such as **"Allow CORS: Access-Control-Allow-Origin"** or **"CORS Unblock"** from the Chrome Web Store and toggle it ON).*

---

### Solution 2: Proxy API Requests via Next.js Rewrites (No Chrome flags needed)

You can proxy API calls through the local Next.js dev server so the browser only talks to `localhost:3000` (bypassing browser CORS completely):

1. **Add a rewrite rule** in [`next.config.js`](file:///C:/Work/qcash-ui/next.config.js#L136):
   ```javascript
   // Inside async rewrites() { ... return [ ...
   {
     source: "/api/:path*",
     destination: "http://internal-service.example.com/api/:path*",
     basePath: false,
   },
   ```

2. **Override the API URL for local dev** in a local env file ([`.env.local`](file:///C:/Work/qcash-ui/.env.local)):
   ```env
   NEXT_PUBLIC_API_URL_DEV_ID=http://localhost:3000/api
   ```

3. **Restart the dev server**:
   ```bash
   yarn dev
   ```

Now requests will be dispatched to `http://localhost:3000/api/...` (same origin) and forwarded server-to-server by Next.js without triggering CORS.

Here is exactly how the fix works under the hood:

---

### The Problem
1. When you open `/v2/landing-page`, the host app loads the federated **`qcash-ui-landing-page`** micro-frontend bundle from the remote server.
2. Inside that bundle, an Axios instance attaches the custom header **`X-Process-Id`** and makes an API call directly to `http://internal-service.example.com/api/...`.
3. Because your browser is on `http://localhost:3000`, the browser classifies this as a **Cross-Origin request** with a custom header and sends an `OPTIONS` (preflight) request to the remote server.
4. The remote gateway at `gym-master` did not include `x-process-id` in its `Access-Control-Allow-Headers` list, so your browser blocked the request before it even reached the API.

---

### The Solution: A 2-Part Reverse Proxy

To bypass the browser's CORS restrictions without modifying the backend gateway or requiring special browser flags, two components were connected:

```
[Browser on localhost:3000]
        │
        │ 1. Interceptor rewrites URL: gym-master/api/... ──► /api/... (Same Origin)
        ▼
[Next.js Dev Server (localhost:3000)]
        │
        │ 2. Next.js rewrites() forwards request (Server-to-Server)
        ▼
[Remote Backend (gym-master OCP)]
```

#### 1. Server-Side: Next.js Reverse Proxy ([`next.config.js`](file:///C:/Work/qcash-ui/next.config.js#L142-L151))
We added rewrite rules to the Next.js dev server:
```javascript
{
  source: "/api/:path*",
  destination: "http://internal-service.example.com/api/:path*",
  basePath: false,
}
```
Any request hitting `http://localhost:3000/api/...` is received by your local Next.js server and forwarded directly to `gym-master` on the server side. **CORS does not exist between servers**, so all headers (`X-Process-Id`, `Authorization`, etc.) pass through smoothly.

#### 2. Client-Side: Dev Request Bridge ([`pages/_app.tsx`](file:///C:/Work/qcash-ui/pages/_app.tsx#L50-L68))
Because the remote micro-frontend code (`qcash-ui-landing-page`) has `http://gym-master.../api` hardcoded in its bundle, the browser would normally still try to send requests directly to the remote URL.

In [`pages/_app.tsx`](file:///C:/Work/qcash-ui/pages/_app.tsx#L50-L68), we added a lightweight dev-only hook that intercepts outgoing `XMLHttpRequest` and `fetch` calls:
```typescript
if (process.env.NODE_ENV === "development" && globalThis.window.location.hostname.includes("localhost")) {
  const devApiPattern = /^https?:\/\/gym-master(-[a-z]+)?\.apps\.ocp-new-dev\.bri\.co\.id\/api/;
  // Automatically reroute gym-master API calls to /api
  ...
}
```
Whenever the remote landing page makes an API call, it gets routed to `/api/...` instead of the cross-origin remote URL.

---

### Why this is safe
- **Zero impact on production**: The interceptor and rewrites only activate when `NODE_ENV === "development"` and the hostname is `localhost`.
- **Works for all micro-frontends**: Any other remote module loaded into the shell that calls `gym-master` will also automatically bypass CORS without any extra configuration or Chrome extensions.
